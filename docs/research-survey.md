## 1. 均衡計算アルゴリズム(CFR 族)
- **Vanilla CFR**(Zinkevich 2007): O(1/√T)。実務では obsolete — 教育・回帰テスト用のみ。
- **CFR+**(Tammelin 2014): RM+(累積 regret を 0 で床)、alternating updates、weight-t 平均。Cepheus が HU-LHE を実質解決。alternating + RM+ は「無料の勝ち」で後続全変種が継承。
- **DCFR**(Brown & Sandholm 2019): 正 regret を t^α/(t^α+1)、負を t^β/(t^β+1)、平均を (t/(t+1))^γ で割引。α=1.5, β=0, γ=2 が canonical、poker subgame で CFR+ 比 ~2–3x。**b-inary 実測では γ=3.0 + power-of-4 平均リセットがさらに良い — 本プロジェクトの default**。
- **Linear CFR**(=DCFR(1,1,1)): 広い bet メニューの tree で頑健。**sampling と組む唯一の選択**(β=0 の負 regret ゼロ化は sampling noise と相性が悪い)。
- **PCFR+ / PDCFR+**: 非 poker EFG では最速だが poker では DCFR が勝つ(2024 年の複数追試で一貫)。A/B 完備のため後日追加。
- **HS-DCFR / DDCFR**(2024): 割引ハイパーパラメータのスケジューリング。HS-DCFR(30)(α=1+3t/n, β=−1−2t/n, γ=30−5t/n)は training-free・<15 行で、固定 iteration 予算での exploitability を桁違いに改善 — poker の tabular SOTA。

## 2. サンプリングと枝刈り
- **MCCFR**(Lanctot 2009): external sampling(traverser 全手・相手/chance サンプル)が汎用最良。full traversal 不可能な巨大 tree(bucketed 全ゲーム)専用。
- **Pluribus レシピ**: Linear MCCFR + 序盤のみ batched discount + negative-regret pruning(regret ≪ 0 の枝を 95% の iteration で skip、最終 street では不可)+ 4-byte int regret。
- **Regret-Based Pruning / Dynamic Thresholding**: 大規模 tree で合計最大 ~2 桁の加速。preflop 規模で効く。
- **Warm starting**(Brown & Sandholm AAAI-16): 任意の戦略対から 1 traversal で warm start、収束保証を損なわない。粗い tree(少サイズ・49-flop)→ 本番の段階解きに直結。

## 3. カード抽象化
- **Lossless suit isomorphism**(Waugh AAAI-13 workshop, BSD): 完全・可逆 index。flop 22,100→1,755、turn/river branch 併合で平均 ~1.7–1.9x(monotone で 24x)。**Mode A では唯一の(可逆)カード抽象化 — 常時 ON**。
- **Imperfect-recall bucketing**(Johanson AAMAS-13): 同メモリで perfect recall を支配。preflop は常に lossless 169。
- **IR-KE-KO レシピ**: flop/turn = k-means + EMD on hand-strength histogram、river = OCHS(8 プリフロップクラスタ対等 equity の L2)。実証済みの標準。
- **Potential-aware EMD**(Ganzfried & Sandholm AAAI-14): 次 street クラスタ上の histogram + 近似 EMD。+2.2–2.6 mbb/h。任意の上積み。
- 規模感: 200–500 buckets/street ≈ Pluribus blueprint 品質、5k–9k ≈ 学術 strong-blueprint。RAM に対する線形ノブとして公開。

## 4. アクション抽象化
- **サイズグリッドはデータ**(pot-% グリッド + geometric 生成器)。1–3 sizes/node で EV のほぼ全て(追加サイズの限界 EV ≈ 0.05% pot、tree は ~125x 膨張し得る)。
- **Pseudo-harmonic translation**: off-tree 対応の標準だが exploitability で nested subgame solving に ~10x 劣る — playing-agent 用 fallback であり solving 技法ではない。**見送り**。
- **Subgame solving**: unsafe re-solve(blueprint reach を種に)は range-vector CFR があれば自明で実務上しばしば最良。Resolve/Maxmargin gadget はどちらも支配的でないため 1 interface の背後に後日。

## 5. 計算高速化
- **Vector-form CFR**(Johanson 2011): per-hand range/CFV ベクトルで public tree を 1 回走査。OpenSpiel 型比 2–3 桁 — **アーキテクチャとして day-1 採用**。
- **Sorted-rank O(n+m) showdown**: build 時に canonical river 毎 rank ソート、solve 時は sweep。evaluator をホットパスから排除。
- **i16 量子化**(i16 + node 毎 f32 scale): ~47% メモリ削減 / ~20–30% 時間、0.1%-pot で精度劣化なし。DCFR の振幅制御が前提条件。
- **rayon 分割並列**: chance branch(turn×river)毎に regret メモリを分割所有、lock/atomic ゼロ。物理コアで線形(memory-bandwidth-bound)。
- **SIMD**: auto-vectorization 優先(`-C target-cpu=native` + `cargo-show-asm` 監査、float reduction は multi-accumulator)、失敗箇所のみ `wide`。nightly `std::simd` 非依存。
- **GPU CFR**: 公表 401x/204x は遅い OpenSpiel 基準比で、hand-optimized CPU vector CFR 比の利得は遥かに小さい。OSS の NLHE 前例なし。**見送り(再訪条件明記)**。
- **Accelerated Best Response**: 全 hand 同時 BR、コスト ≈ CFR 1 iteration。exploitability を停止判定(25 iter 毎、default 0.3% pot、per-player)と抽象化評価の両方に使う。

## 6. Neural 系(Deep CFR / SD-CFR / DREAM / ESCHER / ReBeL / NN leaf)
tree が(抽象化込みで)RAM に収まる限り tabular DCFR が支配(ReBeL の HUNL 品質 ≈ tabular ~125 iteration 分)。**v1 では不採用**。ただし GTO Wizard AI 路線(depth-limited + NN leaf、0.1% pot 級)は将来価値が高いため、**`PostflopModel` trait を専用の継ぎ目として維持**する。

# 調査テーマ別 詳細所見


## CFR アルゴリズム族と均衡計算


### 概要

The CFR family remains the workhorse for poker equilibrium computation, and for a PioSOLVER-class postflop HU-NLHE solver the practical state of the art is Discounted CFR (DCFR) with alternating updates and vectorized range-vs-range traversal. Vanilla CFR (Zinkevich 2007, regret matching, O(1/sqrt(T)) convergence) is obsolete in practice; CFR+ (Tammelin 2014: regret-matching+ clamping cumulative regrets at zero, alternating updates, linearly weighted averaging) was used to essentially solve HU Limit Hold'em (Cepheus, exploitability 0.986 mbb/g, ~900 core-years, ~11 TB of values). DCFR (Brown & Sandholm 2019) with alpha=1.5, beta=0, gamma=2 converges roughly 2-3x faster than CFR+ on no-limit poker subgames and is what the best open-source solvers actually use: b-inary's Rust postflop-solver (AGPL-3.0) uses DCFR with gamma=3.0 and strategy resets at power-of-4 iterations, and TexasSolver (AGPL-3.0) matches PioSolver accuracy (0.275% vs 0.29% pot) while beating its speed on some flop trees. Predictive CFR+ (PCFR+, Farina/Kroer/Sandholm 2021) is the fastest known method on non-poker games but DCFR still wins on poker; PDCFR+ (IJCAI 2024) combines both via optimistic OMD. The most notable 2024 tabular advances are learned/scheduled discounting: DDCFR (ICLR 2024) and training-free Hyperparameter Schedules (HS-DCFR, arXiv 2404.09097) which linearly anneal alpha/beta/gamma over the run and report multi-order-of-magnitude exploitability improvements at fixed iteration budgets, with HS-DCFR(30) recommended for poker.

For very large preflop/full-game trees where full traversals are infeasible, sampling MCCFR is the standard: Lanctot 2009 defines outcome, external, and chance sampling, with external sampling (traverser explores all actions, opponent/chance sampled) the best general choice — constant-factor more iterations for an order reduction in per-iteration cost. Pluribus's blueprint used Linear MCCFR (linear weighting of regrets and averages, discounting applied every 10 minutes for only the first 400 minutes, ~200M iterations) plus negative-regret pruning (skip actions with very negative regret in 95% of iterations); DCFR's beta=0 (zeroing negative regrets) mixes poorly with sampling noise, which is why Linear CFR is preferred with MCCFR. Pure CFR (Gibson) samples a pure strategy profile per iteration and stores regrets as integers, halving memory. Exploitability is measured via a best-response (expectimax) pass; the key efficiency trick is Johanson's Accelerated Best Response: traverse the public tree once computing values for ALL private hands simultaneously against the opponent's full range, with O(n) sorted-rank river evaluation instead of O(n^2) — this cut full-HULHE exploitability from ~years to 76 CPU-days, and in a postflop solver makes an exploitability check cost about the same as one CFR iteration. Industry stopping criteria: PioSolver ships solutions at 0.25-0.5% of pot; GTO Wizard targets ~0.1% (flops 0.21%, turns 0.24%+-0.08%, rivers <0.10% Nash distance); open-source solvers default to 0.3-0.5% of pot exploitability checked every N (e.g. 25) iterations. Deep-learning CFR (Deep CFR, SD-CFR, DREAM, ESCHER, ReBeL) matters for research breadth but not for a tabular solver: ReBeL's HUNL solution quality equals only ~125 tabular CFR iterations, and tabular CFR dominates whenever the (abstracted) tree fits in memory.


### 主要な所見

- DCFR (Brown & Sandholm, arXiv 1809.04040) discounts positive regrets by t^alpha/(t^alpha+1), negative regrets by t^beta/(t^beta+1), and average-strategy contributions by (t/(t+1))^gamma; recommended alpha=1.5, beta=0, gamma=2; converges ~2-3x faster than CFR+ on HUNL subgames. Linear CFR = DCFR(1,1,1); LCFR is more robust in trees with many large-mistake actions (wide bet-size menus) and is the variant to pair with sampling.
- PCFR+ (Farina, Kroer, Sandholm, AAAI 2021, 'Predictive Blackwell Approachability') is the fastest known tabular method on non-poker EFGs, but on poker games DCFR remains fastest — a consistent finding replicated in the 2024 Hyperparameter Schedules paper and PDCFR+ (IJCAI 2024, 'Minimizing Weighted Counterfactual Regret with Optimistic OMD').
- 2024 advances: DDCFR (ICLR 2024 spotlight, code at rpSebastian/DDCFR) learns a dynamic discounting schedule via RL; Hyperparameter Schedules (arXiv 2404.09097) achieves similar gains training-free with linear schedules, e.g. HS-DCFR(30): alpha = 1 + 3t/n, beta = -1 - 2t/n, gamma = 30 - 5t/n; authors recommend HS-DCFR(30) for poker, HS-PCFR+(30) for non-poker; <15 lines of code change.
- What real solvers use: b-inary/postflop-solver (Rust, AGPL-3.0, suspended Oct 2023) uses DCFR with gamma=3.0 and average-strategy resets at power-of-4 iteration counts, f32 storage with f64 accumulation, optional 16-bit-integer compression with one f32 scale factor per node, SIMD-checked inner loops, Rayon multithreading, suit-isomorphism collapsing. Benchmarks (Ryzen 7 3700X, 16 threads, to 0.5% pot exploitability): 21.1s / 1.25GB in f32 mode, 26.1s / 660MB in i16 mode. TexasSolver (C++, AGPL-3.0): 172s vs PioSolver's 242s on an SPR=10 flop tree at ~0.275% pot accuracy but 1600MB vs Pio's 492MB. PioSolver itself does not disclose its variant (community: CFR+/Pure-CFR-class); it needs 0.5-8GB RAM for typical trees and scales linearly with physical cores (rivers are single-threaded in Pio).
- Sampling for huge trees: Lanctot 2009 (NeurIPS) MCCFR — external sampling explores all traverser actions and samples opponent/chance (best general choice, probabilistic O(1/sqrt(T)) regret bound); outcome sampling touches one trajectory (highest variance, needed only for online/model-free settings); chance sampling samples only board cards. Pluribus blueprint: external-sampling Linear MCCFR, discounting regrets and averages by multiplicative factors every 10 min only for the first 400 min, ~200M iterations, plus negative-regret pruning (skip actions with extremely negative regret in 95% of iterations, never on the final betting round).
- Exploitability computation: naive expectimax is linear in game-tree size but must be vectorized over ranges to be practical — Johanson's Accelerated Best Response (IJCAI 2011) computes EVs for all private hands at once against the opponent's whole range, with hand-isomorphism reuse and O(n log n)/O(n) sorted-rank showdown evaluation, reducing full-HULHE exploitability from ~10 years (naive) to 76 CPU-days; in a range-based postflop solver, one exploitability check costs roughly one CFR iteration. Local Best Response (Lisy & Bowling) gives a cheap lower bound on exploitability for full-game strategies.
- Stopping criteria in practice: PioSolver ships 0.25-0.5% of pot; GTO Wizard AI: flops 0.21%, turns 0.24% +- 0.08%, rivers <0.10% Nash distance (exploitability/pot); common open-source default is 0.3-0.5% of pot with exploitability evaluated every ~25 iterations; the academic 'essentially solved' bar (Cepheus) is <1 mbb/hand. Cepheus itself: CFR+, 24 trillion hands over ~70 days on 200 nodes x 24 cores, <11TB of counterfactual values, final exploitability 0.986 mbb/g.
- CFR+ specifics (Tammelin, arXiv 1407.5042): regret-matching+ (cumulative regrets floored at 0), alternating player updates, linear (weight-t) strategy averaging; reference code from U. Alberta is BSD-licensed. Alternation + RM+ are essentially free wins and are inherited by DCFR/PCFR+.
- Numerics: f32 regrets/strategy with f64 summation is proven adequate (postflop-solver); Pure CFR (Gibson, open-pure-cfr on GitHub) stores regrets as integers for ~half memory and converges probabilistically; 16-bit-int quantization with per-node f32 scaling works well specifically because DCFR's discounting keeps magnitudes controlled; Cepheus used compressed fixed-point storage on disk.
- Average vs current strategy: standard CFR guarantees only average-strategy convergence — last iterates of RM/RM+/CFR can cycle or diverge even in normal-form games (Lee et al. 2021; Farina et al. 2024 'RM+: (in)stability'); in practice CFR+'s current strategy is often near-equilibrium, but a correct solver must maintain the gamma-weighted average. Last-iterate alternatives (Reg-CFR, extragradient/predictive RM+, adaptive reward transformation, arXiv 2509.13653) remove the average-strategy memory cost but are not yet standard in production solvers.
- Deep CFR family relevance: Deep CFR (Brown 2019) converges with 2-3 orders of magnitude fewer samples than lossless abstraction and matches a 3.6M-cluster abstraction; SD-CFR removes the policy net and reconstructs the average strategy from stored value nets (lower exploitability than Deep CFR); DREAM adds learned baselines for model-free variance reduction; ESCHER (McAleer, Farina, Lanctot, Sandholm, ICLR 2023) eliminates importance sampling via a history value function with orders-of-magnitude lower regret-estimate variance; ReBeL (RL+search) reaches quality equal to only ~125 full-game tabular CFR iterations in HUNL — none of these beat tabular DCFR when the tree fits in RAM, so they are out of scope for the core solver but relevant as a future 'neural value function at leaves' extension (the GTO Wizard AI approach: depth-limited solving with NN leaf values, no card abstraction, ~0.1% pot accuracy, beat Slumbot by 19bb/100).
- Licenses of discussed projects: b-inary postflop-solver / wasm-postflop / desktop-postflop = AGPL-3.0 (read for ideas, do NOT copy code); TexasSolver = AGPL-3.0 (dual commercial); JoakimMich/opensolver (Rust DCFR postflop solver with 'UPI' Universal Poker Interface — a useful interface-design reference); noambrown/poker_solver (C++/Python river solver with CFR, CFR+, DCFR, ES-MCCFR, exploitability tools) = MIT (safe to reuse); U. Alberta CFR+ reference code = BSD; rggibson/open-pure-cfr = license not verified, check before reuse; DeepMind OpenSpiel (many CFR variants incl. CFR+, MCCFR, exploitability utilities) = Apache-2.0 (safe reference).

### 本プロジェクトへの推奨

1) Core postflop algorithm: implement vectorized range-vs-range CFR with a pluggable 'regret discounting policy' trait. Ship three built-in policies: CFR+ (RM+, alternating updates, weight-t averaging), DCFR(alpha=1.5, beta=0, gamma=2 default; make gamma=3 selectable — b-inary found it better in practice), and Linear CFR. Add PCFR+ and an HS-DCFR-style linear schedule (alpha = 1 + 3t/n, beta = -1 - 2t/n, gamma = 30 - 5t/n) behind the same trait — the schedule is <15 lines and is the current tabular SOTA for poker. Always use alternating updates and suit-isomorphism collapsing on turn/river cards.

2) Preflop/full-game solving: use external-sampling MCCFR with Linear CFR weighting (not beta=0 discounting — zeroed negative regrets interact badly with sampling noise), applying the discount in periodic batches like Pluribus (every k iterations, only during the first phase of the run) and negative-regret pruning (skip regret << 0 branches in ~95% of iterations, never on the river). Structure the preflop solver so postflop continuation values can come from either checkdown-EV, a solved postflop cache, or (later) a neural value function — this is the axis where ReBeL/GTO-Wizard-style methods plug in.

3) Exploitability: implement Johanson-style accelerated best response as a first-class operation sharing the solver's vectorized traversal kernels (evaluate all hero hands vs villain's full range in one pass; O(n log n) sorted-rank showdown evaluation). Run it every ~25 iterations; stop at a user-set target with default 0.3% of starting pot (industry range: Pio 0.25-0.5%, GTO Wizard ~0.1-0.3%). Report exploitability in both %-of-pot and mbb/hand.

4) Numerics/memory: store regrets and average strategy as f32 with f64 accumulators in dot products/sums; offer an i16-quantized storage mode with one f32 scale per node (b-inary measured ~47% memory reduction for ~20% slowdown) — this pairs specifically with DCFR since discounting bounds magnitudes. Consider Pure-CFR-style integer regrets only for the MCCFR path. Keep the average-strategy buffers (last-iterate-only operation is not yet trustworthy), but expose 'current strategy' output for debugging.

5) Architecture for extensibility: (a) separate the abstract game-tree/infoset layer from hold'em-specific evaluation so other variants slot in; (b) make rake a terminal-node payoff transform and ICM a payoff-mapping at terminal utilities (both orthogonal to the CFR loop); (c) copy the 'UPI' (Universal Poker Interface) idea from opensolver for viewer/tooling integration. Parallelize with Rayon over chance branches (flop/turn/river deals) like postflop-solver; expect linear scaling with physical cores.

6) License hygiene: the two most instructive open-source solvers (b-inary postflop-solver, TexasSolver) are AGPL-3.0 — study designs and benchmarks but write all code from scratch; safe-to-reuse references are noambrown/poker_solver (MIT), OpenSpiel (Apache-2.0), and U. Alberta CFR+ (BSD). Skip Deep CFR/DREAM/ESCHER for v1; they only pay off when trees cannot fit in memory even abstracted.

## 抽象化技法(カード抽象化・アクション抽象化・サブゲーム solving)


### 概要

Abstraction for HU-NLHE solving splits cleanly into two regimes, matching your two targets. (a) For exact postflop solving from a given flop (PioSOLVER-style), the standard is NO lossy card abstraction at all: only action abstraction (a hand-picked grid of bet sizes) plus lossless suit isomorphism on chance branches (merging strategically identical turn/river deals, e.g. the two non-dealt suits on a monotone flop). This is verified computationally: 22,100 raw flops collapse to 1,755 canonical flops, 270,725 4-card boards to 16,432, and 2,598,960 5-card boards to 134,459. Kevin Waugh's "Fast and Optimal Hand Isomorphism" algorithm (AAAI-13 workshop; BSD-licensed C reference implementation kdub0/hand-isomorphism) gives a perfect (hole-free, invertible) index over hand+board combos: 169 preflop, 1,286,792 flop, 55,190,538 turn, 2,428,287,420 river — 1.55x tighter than Hyperborean's indexing and 3.5x tighter than Tartanian's, and ~3.5x faster to compute. Memory for exact postflop HU trees is modest: PioSOLVER cites ~1.9 GB for a wide-range HU single-raised pot with one sizing and 5.9 GB for a 25bb HU tree with 2 bet sizes everywhere; 16 GB covers almost all postflop configs; commercial accuracy targets are 0.1–0.5% of pot exploitability. The open-source Rust reference here is b-inary/postflop-solver (AGPL-3.0-or-later, development suspended Oct 2023): DCFR with gamma=3.0, f32 storage with optional 16-bit-integer + per-node f32-scale compression, turn/river isomorphism, claimed faster than PioSOLVER/GTO+.

(b) For full preflop solving you must abstract postflop. The academic state of the art is imperfect-recall, distribution-aware bucketing: keep preflop lossless (169 buckets), then k-means over equity-distribution features. Johanson et al. (AAMAS-13) showed imperfect recall dominates perfect recall at equal memory (IR-169-9000-9000-9000 vs PR-10-10-10-10, both ~57M infosets), with the best combo being k-means with Earth Mover's Distance on hand-strength histograms for flop/turn and k-means on OCHS (L2 over an 8-dimensional vector of equities vs 8 preflop opponent clusters) for the river. Ganzfried & Sandholm (AAAI-14) improved flop/turn bucketing with potential-aware abstraction — histograms over NEXT-round clusters with EMD ground distances, using a fast custom EMD approximation — winning by 2.2–2.6 mbb/h with 169/5,000/5,000/5,000 buckets; this pipeline fed Libratus/Pluribus-era agents. Pluribus's blueprint used only 200 buckets per postflop street (k-means on domain features) and 1–14 pot-fraction raise sizes (664.8M action sequences, <0.5 TB RAM, ~8 days on 64 cores, ~$144 cloud cost) — coarse blueprints are fine when real-time search fixes the details (Pluribus searched with lossless current-round abstraction + 500 buckets for future rounds). Commercial preflop solvers (MonkerSolver, Simple Preflop Holdem) do the same: abstraction-free preflop solving needs hundreds of GB to TBs of RAM, so they bucket postflop streets, with the abstraction size chosen against available RAM. Action-side, the pseudo-harmonic mapping f(x)=((B-x)(1+A))/((B-A)(1+x)) is the standard off-tree translation, but Brown & Sandholm's nested subgame solving beats it by ~10x in exploitability (119–150 vs 1,465 mbb/h); safe re-solving (Resolve/Maxmargin/Reach gadgets) matters mainly for playing agents, not for computing/inspecting equilibria.


### 主要な所見

- Canonical board counts (verified by direct enumeration under the 24 suit permutations): 1,755 flops (from 22,100), 16,432 turn boards (from 270,725), 134,459 river boards (from 2,598,960); preflop hole-card combos: 169 (from 1,326).
- Waugh's hand-isomorphism indexing (rank sets via colex + rank groups + suit-configuration multiset-colex) is perfect and invertible: index sizes 169 preflop, 1,286,792 flop, 55,190,538 turn, 2,428,287,420 river hand+board combos; 1.22x/1.37x/1.55x smaller than Hyperborean and 2.36x/2.91x/3.50x smaller than Tartanian on flop/turn/river, with ~3.5x faster indexing; reference C library kdub0/hand-isomorphism is BSD-style licensed (permissive, safe to port).
- Johanson et al. AAMAS-13 (limit HE): imperfect-recall abstractions beat perfect-recall at equal memory. PR-10-10-10-10 and IR-169-9,000-9,000-9,000 both have ~57.3M infosets, but IR allows a lossless 169-bucket preflop. Best pipeline: k-means+EMD on hand-strength histograms (flop/turn) + k-means OCHS on river (IR-KE-KO was undefeated in crosstable and least exploitable by CFR-BR). OCHS = 8 equities vs 8 preflop opponent clusters (themselves built by EMD clustering of the 169 hands), compared with L2; 1-D EMD computes in one pass over the histogram.
- Ganzfried & Sandholm AAAI-14 potential-aware imperfect-recall abstraction: flop/turn hands represented as histograms over next-round clusters (non-ordinal ground distance = EMD between next-round equity histograms), clustered by k-means with a fast custom approximate multi-dimensional EMD (exact EMD is far too slow). With 169/5,000/5,000/5,000 buckets it beat the prior best distribution-aware abstraction by 2.58±1.56 and 2.22±1.28 mbb/h in HUNL; this is the abstraction style used by Tartanian7/Libratus-era blueprints.
- Libratus: no card abstraction at all on rounds 1-2 of the blueprint; lossy buckets only on turn/river of the blueprint; from the flop onward it used nested subgame solving with no information abstraction in real time. Pluribus blueprint: lossless preflop (169) + only 200 buckets per postflop street (k-means on domain-specific features); real-time search used lossless abstraction for the current street and 500 buckets per future street; blueprint had 664,845,654 action sequences (413.5M reached), trained ~8 days on a 64-core node in <0.5 TB RAM (~$144 cloud), regrets stored as 4-byte ints, Linear-CFR discounting only for the first 400 minutes, plus 95% skip of actions with regret < -300M.
- Action abstraction: Pluribus used 1-14 pot-fraction raise sizes per node (most on the first betting round, at most 3 first-raise sizes on turn/river, e.g. 0.5x/1x pot and all-in; 1-6 sizes in search subgames). GTO Wizard: trees run ~700K to ~87M nodes and a few extra sizes per node can inflate the tree ~125x; they solve to Nash distance 0.1-0.3% of pot; their dynamic-sizing (one well-chosen size) loses only ~0.05% pot on the river vs a full size grid; geometric sizing (equal pot-fraction each remaining street) is the EV-maximizing baseline for range bets. Practical takeaway: 1-3 well-chosen sizes per node captures nearly all EV.
- Action translation: pseudo-harmonic mapping (Ganzfried & Sandholm IJCAI-13), f_{A,B}(x) = ((B-x)(1+A))/((B-A)(1+x)) = probability of mapping off-tree size x to the smaller abstract size A; derived from the Nash equilibrium of the clairvoyance game; median mapped size ~0.34 pot (vs 0.5 for arithmetic). But in Brown & Sandholm's NLFH benchmark, randomized pseudo-harmonic translation was exploitable for 1,465 mbb/h vs 119-150 mbb/h for nested subgame solving - translation is a fallback for playing agents, not a solving technique.
- Subgame solving (Brown & Sandholm NIPS-17): unsafe re-solving (assume blueprint reach distribution) is simple and often best in practice (65.6 vs Resolve 179.6 mbb/g exploitability at 200 flop buckets) but can blow up (396.8 vs 23.1 mbb/g at 30,000 buckets). Safe gadgets: Resolve (CFR-D), Maxmargin, Reach-Maxmargin, and Estimate+Distributional variants; best safe method reached 8.8 mbb/g vs trunk's 41.4 in large flop hold'em with 30k buckets. 2026 follow-up work (arXiv 2601.17131) shows max-margin is NOT uniformly better than resolving; DeepStack preferred the resolving gadget.
- Depth-limited solving (Modicum, NeurIPS-18): blueprint = 5 GB of 4-byte floats via MCCFR in 700 core-hours; at the depth limit the opponent picks among 4 continuation strategies (blueprint; fold-probability x10 renormalized; call-biased; raise-biased); 10 values per round-1 leaf state stored in 240 MB; beat Baby Tartanian8 (which used 2M core-hours + 18 TB RAM) and Slumbot (250K core-hours) using a 4-core CPU + 16 GB. Only needed if you build a real-time playing agent, not for a research equilibrium solver.
- Exact-postflop solver memory (PioSOLVER docs): ~1.9 GB for a wide-range (90% vs 70%) HU single-raised-pot tree with one 2/3-pot sizing, 5.9 GB for a 25bb HU tree with 2 sizes (30%/60%) everywhere; 16 GB suffices for nearly all postflop trees; typical solution quality ~0.1-0.5% pot exploitability ('1bb/100' scale). PioSOLVER uses no lossy abstraction whatsoever postflop.
- Preflop solving without postflop abstraction needs hundreds of GB to TBs of RAM (Simple Preflop Holdem docs); all commercial preflop solvers (MonkerSolver, Simple Preflop) therefore bucket postflop streets, exposing abstraction size as a user knob traded against RAM (large PLO preflop solves need 64GB+ even with abstraction).
- DCFR best hyperparameters (Brown & Sandholm AAAI-19): alpha=1.5, beta=0, gamma=2 (positive-regret discount t^1.5/(t^1.5+1), negative regrets zeroed-discounting via beta=0, average strategy weighted by (t/(t+1))^gamma). b-inary's Rust solver ships gamma=3.0 and resets the cumulative strategy at power-of-4 iteration counts.
- Licenses: b-inary/postflop-solver and wasm-postflop = AGPL-3.0-or-later (development suspended; author went commercial) - read for ideas, do NOT copy code unless you accept AGPL; bupticybee/TexasSolver (C++ 'discounted CFR++') = AGPL-3.0 with commercial-license requirement; kdub0/hand-isomorphism = permissive BSD-style (safe to port/reuse with attribution); JoakimMich/opensolver (Rust, DCFR, 'UPI' protocol) exists as another reference.

### 本プロジェクトへの推奨

1) Architect two solving modes sharing one game-tree/CFR core. Mode A (exact postflop): fixed flop, full 1,326-combo range representation per player (range-vs-range vector CFR over 52x51/2 hands, not per-infoset tables), no card bucketing, suit-isomorphism merging of turn/river chance branches (expect ~1.7-1.9x node reduction on average, up to 24x on monotone boards), configurable bet-size grid. Budget ~2-6 GB/tree; offer b-inary-style 16-bit-int + f32-scale node compression to halve it. Mode B (preflop blueprint): trunk = full preflop tree, postflop streets bucketed via a pluggable `CardAbstraction` trait.

2) Build a hand-indexing crate first, porting Waugh's algorithm (BSD - safe to port; verify against his published sizes: 169 / 1,286,792 / 55,190,538 / 2,428,287,420 and board counts 1,755 / 16,432 / 134,459, which we re-verified by enumeration). Everything else (equity tables, bucketing, strategy storage) keys off these indices.

3) Bucketing pipeline for Mode B, in increasing sophistication: (i) E[HS]/E[HS^2] percentile buckets (1 day of work, good baseline); (ii) k-means+EMD on 50-bin hand-strength histograms for flop/turn and k-means on 8-dim OCHS vectors with L2 for river, imperfect recall, lossless 169 preflop - this is the proven IR-KE-KO recipe; (iii) optionally potential-aware EMD (histograms over next-street clusters) for flop/turn. Sensible sizes: 200-500 buckets/street reproduces Pluribus-blueprint quality; 5,000-9,000/street matches the academic strong-blueprint regime; make it a parameter since memory scales linearly in buckets x action sequences.

4) Use DCFR (alpha=1.5, beta=0, gamma=2; expose gamma - b-inary found 3.0 better in practice) as the default postflop algorithm behind a `Solver` trait, with external-sampling MCCFR + Linear-CFR-style early discounting + negative-regret pruning for the Mode-B blueprint. Store regrets as f32 (or 4-byte ints Pluribus-style in the MC path).

5) Action abstraction as data, not code: per-node size grids in pot fractions with geometric-sizing generators; default to 1-3 sizes/node (evidence says marginal EV of more sizes is ~0.05% pot); include an optional pseudo-harmonic translation module only for future bot-play/evaluation tooling.

6) Subgame solving: implement unsafe re-solving first (trivial given range-vector CFR: seed the subgame with blueprint reaches) for refining preflop-blueprint postflop play; add the Resolve gadget (CFR-D) and Maxmargin as alternative `GadgetBuilder`s later - literature says neither dominates, so keep both behind one interface. Depth-limited multi-valued-state solving (Modicum) is only worth building if you later want a real-time playing agent on small hardware.

7) License hygiene: treat b-inary/postflop-solver and TexasSolver as design references only (AGPL) - reading for architecture ideas (bit-packed node layout, compression, isomorphism handling) is fine, but no code copying unless the project adopts AGPL. Waugh's hand-isomorphism (BSD) may be ported directly with attribution.

8) Validation targets: exact-mode exploitability <0.1-0.3% pot (compute via best-response/CFR-BR pass, which also validates abstractions); compare preflop outputs against published HU ranges; unit-test isomorphism counts against the verified canonical numbers.

## 既存 OSS ソルバーのアーキテクチャ研究


### 概要

The clear architectural gold standard for our project is b-inary/postflop-solver (Rust, development suspended Oct 2023, licensed AGPL-3.0-or-later — confirmed). Its speed comes from a stack of deliberate decisions: no card abstraction at all postflop, but suit-isomorphic turn/river deals are merged (e.g. on a monotone flop, 2 of 3 non-dealt suits are skipped); vectorized range-based CFR using Discounted CFR with gamma raised to 3.0 (vs the paper's 2.0) plus cumulative-strategy resets at power-of-4 iteration counts; f32 storage with f64 accumulation; an optional 16-bit-integer compression mode storing each node's values as i16 plus a single f32 scale factor per node (cuts memory ~47%: 1.25 GB to 660 MB on the benchmark spot, at ~25% time cost); rayon multithreading with a lightweight MutexLike wrapper; and hand-audited unsafe/SIMD hot loops. In b-inary's published benchmark (Ryzen 7 3700X, PioSOLVER "3betpotFAST" preset, 0.1% pot exploitability target), Desktop Postflop solved in 44.4 s / 1.27 GB at 6 threads vs PioSOLVER 60.1 s / 1.41 GB and GTO+ 67.7 s / 705 MB, and 27.9 s at 16 threads — an open-source solver genuinely beating the commercial tools. The same crate is reused unchanged by wasm-postflop (wasm-pack + nightly Rust, ~2x slower in-browser, capped at 4 GB wasm32 memory) and desktop-postflop (Tauri shell around the same Vue UI, native speed, unlimited memory) — proof that a clean core-library/frontend split gives WASM, desktop, and CLI targets for free. Its API is a good template: PostFlopGame::with_config(CardConfig, ActionTree) -> allocate_memory(enable_compression) -> solve(max_iter, target_exploitability), then a navigation/query layer (play, apply_history, back_to_root, cache_normalized_weights, strategy, equity, expected_values, compute_exploitability, compute_mes_ev) sitting on generic Game/GameNode traits, with bincode(+zstd) serialization. It is also uniquely able to model the bunching effect (up to 4 folded players), at the cost of terminal-node complexity going from O(#OOP + #IP) to O(#OOP x #IP).

The comparison points confirm the design tradeoffs. bupticybee/TexasSolver (C++, AGPL-3.0 with a paid commercial-license option) claims to beat PioSOLVER on flop solves (172 s vs 242 s at SPR=10, 6 threads) but uses 3x more memory (1600 MB vs 492 MB), and in b-inary's neutral benchmark it was the slowest and most memory-hungry entry (285.9 s / 2.84 GB); its text-command config format (set_pot, set_effective_stack, set_board, set_range_ip/oop, set_bet_sizes oop,flop,bet,50 ..., build_tree, start_solve) is a reasonable model for a scriptable console interface. google-deepmind/open_spiel (Apache-2.0) sits at the opposite pole: a fully generic Game/State API (legal_actions, apply_action, chance_outcomes, explicit chance player, information-state vs observation distinction) that lets one tabular CFR/CFR+/MCCFR/Deep-CFR/exploitability implementation run on any game — but the price is enormous: recent papers (LiteEFG, GPU-accelerated CFR) measure specialized implementations up to ~203x faster than OpenSpiel's C++ CFR and ~401x faster than its Python CFR. The lesson: copy OpenSpiel's trait-level decoupling of algorithm from game, but never its per-State object allocation model — CFR must operate on flat vectors over entire ranges, not one State object per history.

On hand evaluation, the strongest fit is b-inary/holdem-hand-evaluator (MIT, pure Rust, zero deps): ~212 KB lookup tables with script-generated magic constants, an incremental Hand struct (add_card/evaluate), and ~1.2 billion evals/s single-threaded on a Ryzen 9 5950X — roughly 20-25x faster than rs-poker's ~50M hands/s (20 ns/5-card, <25 ns/7-card; Apache-2.0). aya-poker (Zlib OR Apache-2.0 OR MIT, OMPEval-derived PHF tables) is the best multi-variant option (Omaha, short-deck, lowball, badugi), and the poker crate (MIT, a port of Python treys) is not competitive for solver workloads. Important nuance: in a well-designed solver, raw evaluator speed is secondary — postflop solvers precompute river hand strengths per board runout once and use sorted-range O(n+m) terminal-node evaluation, so the evaluator only runs during setup. Adjacent resources: pokerkit (MIT, U-of-T CPRG Python library) is the best reference for modeling multi-variant poker rules; PokerRL (MIT) for distributed deep-CFR worker architecture; ericgjackson/slumbot2019 has C++ CFR+/MCCFR/Targeted-CFR implementations from the Slumbot author (license not clearly advertised — verify before reuse), and Slumbot's free no-auth HTTP API is a ready-made head-to-head benchmark for any HU-NLHE agent we build.

2) Layered architecture (postflop-solver's proven shape, generalized): (a) a `Game`/`GameNode` trait layer that the CFR engine is generic over — this is where variant extensibility lives; (b) a concrete HU-NLHE implementation with an abstract `ActionTree` (bet-size grammar per street/position: bet/raise/donk sizes, all-in threshold, add-all-in flag) kept separate from `CardConfig` (ranges + board); (c) a solver layer exposing solve/solve_step/target-exploitability stopping; (d) a navigation+query layer (play/apply_history/back_to_root, cached normalized weights, strategy/EV/equity as flat f32 vectors) that the viewer/tooling consumes; (e) thin frontends (CLI first; the crate boundary makes WASM/Tauri viewers nearly free later). Make terminal-node payoff evaluation a pluggable trait — that is exactly where rake models (chip EV minus rake function of pot) and ICM (map chip outcomes through payout structure) enter without touching the CFR core.

3) CFR engine: vectorized range-based DCFR, not per-infoset tabular CFR. Store regrets and cumulative strategy in flat contiguous arenas indexed by precomputed node offsets; update whole ranges with SIMD-friendly f32 loops, accumulate in f64. Implement DCFR with configurable (alpha, beta, gamma), defaulting to alpha=1.5, beta=0 (or 0.5), gamma in [2,3] — replicate postflop-solver's gamma=3.0 + power-of-4 strategy resets as the tuned default; leave hooks for CFR+ and dynamic schedules (DDCFR) as alternate algorithm impls behind a Solver trait. Parallelize with rayon across chance branches (turn/river deals) using a cheap spin/atomic MutexLike rather than std::sync::Mutex.

4) Memory: implement the 16-bit quantization option from day one (i16 values + one f32 scale per node), since it halves memory for ~25% time cost and its presence shapes the storage API (allocate_memory(enable_compression), memory_usage() -> (u64, u64) computed before allocation). Exploit turn/river suit isomorphism in the tree builder. Serialize with bincode + zstd.

5) Hand evaluation: depend on holdem-hand-evaluator (MIT, zero deps, ~212 KB LUT, ~1.2G evals/s) for NLHE, or vendor its table-generation scripts if we want control; adopt its incremental Hand design. Do not write a two-plus-two 100+ MB table evaluator — unnecessary. For future variants, aya-poker's OMPEval-style PHF approach is the fallback. Critically, design terminal showdown evaluation as precomputed-per-river sorted-rank sweeps so the evaluator is off the hot path.

6) Do NOT adopt OpenSpiel's per-State-object model for the core engine (100-400x measured slowdown vs specialized CFR), but do copy its conceptual separations: explicit chance nodes, information-state vs observation, algorithm/game decoupling, and its exploitability/best-response tooling as a correctness oracle — validating our exploitability numbers against OpenSpiel on small games (Kuhn/Leduc) is a cheap, high-value test strategy.

7) Benchmarking plan: replicate b-inary's PioSOLVER '3betpotFAST' benchmark spot (targets: <=45 s at 6 threads, <=1.3 GB uncompressed / <=700 MB compressed, 0.1% pot exploitability) and use the free Slumbot HTTP API for head-to-head agent evaluation. Adopt TexasSolver-style imperative text config for a reproducible console/batch interface, and pokerkit as the design reference when we generalize the rules engine to other variants.

## プリフロップ solving・レーキ・ICM


### 概要

Preflop/full-game HU-NLHE solving is done three ways in practice, and the commercial tools map cleanly onto them. (1) Full-tree solving with flop sampling: PioSOLVER Edge builds the entire preflop+postflop tree but replaces the 1,755 strategically-distinct flops (22,100 raw) with weighted subsets of 25/49/75/95/184 flops; results are reported as an "almost exact match" to solving all 1,755, but it still needs 64GB RAM minimum (128GB recommended) and long solve times. (2) Card-bucketed abstraction + MCCFR: MonkerSolver merges strategically similar hand/board combos into imperfect-recall buckets and runs Monte Carlo CFR over the abstract full game; typical NLHE preflop solves take 12–48h on 64GB+ desktops, weeks on servers, and it supports multiway, ICM and rake (% + cap). (3) Postflop-model solvers: HoldemResources Calculator historically used equity/showdown terminal models, and HRC v3 now builds abstracted postflop trees with 64–16,384 imperfect-recall buckets (equity + equity-realization features per Johanson et al. 2013), solved by sampling, with full ICM/KO and card-bunching support; Simple Preflop Holdem sits at the full-tree extreme ("hundreds of GB to TBs of RAM", cluster service). GTO Wizard ships a precomputed library (12 stack depths x 11 rake structures x 4 open sizes) plus a neural "GTO Wizard AI" for custom rake and ICM postflop solving.

Rake is universally modeled as min(rake% x pot, cap) subtracted from the pot at terminal nodes before distribution, with a "no flop, no drop" flag zeroing rake on pots that end preflop (GG Poker is the notable exception, raking 3-bet+ preflop pots, which measurably changes strategy). Real structures span NL50 = 5%/4bb-cap to NL500 = 5%/0.6bb-cap. Rake makes the game general-sum (payoffs sum to -rake(z), action-dependent), so the O(1/sqrt(T)) CFR Nash guarantee formally fails; however Gibson et al. (arXiv:1305.0034) prove CFR still avoids iteratively strictly dominated strategies and show 2-player non-zero-sum CFR lands very close to equilibrium empirically — and every commercial solver just subtracts rake at terminals and runs CFR/DCFR anyway, reporting per-player best-response exploitability. ICM (Malmuth-Harville) converts terminal chip stacks into $ equities: naive enumeration dies around 15 players (optimized exact ~25-30), HRC published a high-accuracy large-field approximation, and GTO Wizard's 2024 algorithm computes it with ~3e-9 relative error for thousands of players with no abstraction. FGS replaces ICM-at-terminal with a recursive Nash solve of 1-N future hands (blinds moved) before applying ICM, worth ~+0.3% ROI per HRC's measurements. Crucially, with exactly two players and payouts (p1,p2), MH-ICM equity is affine in stack — EV_i = p2 + (p1-p2)*s_i/S — so pure HU ICM is strategically identical to chip-EV; ICM only bites HU when embedded in a larger structure (multi-table, PKO bounties, satellites). Bunching (card removal from folded hands) is irrelevant for pure HU but large for multiway short-stack spots (HRC: folded-to-SB at 7.5bb sees aces +26.5% frequency, ~24% of the naive shove range turns unprofitable). The clean design answer to the key question: make terminal evaluation a build-time pipeline — game rules produce a small per-terminal outcome set (win/tie/lose chip deltas), a RakeModel trait transforms the pot, a UtilityModel trait maps resulting chip stacks to per-player utility ($, ICM, bounty) — and bake the results into per-terminal constant payoff vectors so the CFR hot loop never makes a dynamic-dispatch call.


### 主要な所見

- Preflop full-tree solving via flop subsets (PioSOLVER approach): 22,100 flops reduce to 1,755 strategically distinct via suit isomorphism; Pio ships weighted subsets of 25/49/75/95/184 flops whose preflop EVs are an 'almost exact match' to the full 1,755-flop solve; GTO Wizard uses 25/49/85/184 subsets. Preflop EV = weight-averaged EV across subset flops.
- PioSOLVER preflop hardware: 64GB RAM is the stated absolute minimum for practical preflop solving (32GB only for toy trees), 128GB recommended for more sizings/complex postflop; the preflop solver requires the Edge edition; tree-size estimation is available before building.
- MonkerSolver: abstraction (imperfect-recall card bucketing) + Monte Carlo CFR over the full game; abstraction panel pre-estimates RAM; community guidance: 64GB+ RAM to use the preflop solver comfortably; typical NLHE preflop solves 12-24h (fast machine) to 48h+ (slow); big PLO/multiway sims take weeks on servers; supports multiway, ICM/MTT, and rake configured as percentage + cap (example unit conversion: 2000 mchips = 1bb); recommended convergence target ~1.5-2.0 'volatility'.
- HRC (HoldemResources Calculator) v3/v4: preflop solver with modeled postflop via imperfect-recall abstractions of 64 to 16,384 buckets (Classic tier capped at 256 buckets and 25,000-node trees, effective to ~25-30bb; Pro unlimited); buckets encode equity AND equity realization on future streets (citing Johanson et al. 2013 state-space abstraction work); postflop uses Monte Carlo sampling with 4 suit-abstraction levels (Strict/Balanced/Relaxed/LQ-16k); models ICM, KO/bounties, and full card bunching inside postflop evaluation.
- Simple Preflop Holdem (SimplePoker): full-tree preflop calculations 'require from hundreds of gigabytes to tens of hundreds of terabytes of RAM'; they sell cluster solves as a service; with postflop abstractions the RAM need drops; solves all 1,755 significant flops and maps results onto the 22,100 raw flops.
- GTO Wizard solution library dimensions: preflop cash solutions cover 12 stack depths, 11 rake structures (NL25, NL50, NL100, NL200, NL500, NL1k, NL2k, NL5k, NL10k, live, plus rake-free cEV), and 4 opening sizes (2x/2.25x/2.5x/3x). Example rake structures: NL50 = 5% rake, 4bb cap; NL500 = 5% rake, 0.6bb cap; GG NL50 = 5% up to 8bb including raked 3-bet preflop pots.
- Rake model standard: rake = min(rake_rate * pot, cap) deducted from the pot at terminal nodes (winner pays); 'no flop, no drop' = pots ending preflop are unraked on most sites; GG Poker deviates by raking preflop pots after a 3-bet, which GTO Wizard notes 'significantly changes the optimal strategy' (more incentive to end hands preflop).
- Strategic effect of rake (GTO Wizard raked-solutions analysis): rake mostly penalizes the defender closing the action -> defender calls less, aggressor bets more with trash (measured 36% -> 45% betting frequency for trash hands as rake rises), ranges polarize; preflop at high-rake stakes, 3-betting increases to win pots before postflop rake applies, and BB defense tightens.
- Rake breaks zero-sum: payoffs sum to -rake(z), which is action-dependent, so raked poker is a 2-player general-sum game and CFR's Nash-convergence guarantee formally fails. Gibson et al., 'Regret Minimization in Non-Zero-Sum Games...' (arXiv:1305.0034) prove CFR still eliminates iteratively strictly dominated actions/strategies and demonstrate that in 2-player non-zero-sum games CFR yields strategies 'very close to equilibrium' empirically. Commercial practice: subtract rake at terminals, run CFR/CFR+/DCFR unchanged, verify via per-player best-response exploitability (the two players' exploitabilities no longer mirror each other).
- DCFR canonical hyperparameters from Brown & Sandholm (arXiv:1809.04040): alpha=1.5, beta=0, gamma=2 (positive regrets discounted by t^1.5/(t^1.5+1), negative regrets by beta-weighting with beta=0, average strategy by (t/(t+1))^gamma). The Rust postflop-solver library deviates with gamma=3 plus cumulative-strategy resets at power-of-4 iteration counts and reports this works well.
- Reference point for full-game solving scale: Cepheus essentially solved HU LIMIT hold'em (3.16e17 states) with CFR+ to <1 mbb/g exploitability using 200 nodes x 24 cores (4,800 cores) for 68 days, 32GB RAM + 1TB disk per node, game partitioned into 110,565 subgames — full-game HU no-limit without abstraction remains intractable; bet-size restriction + flop sampling or card bucketing is mandatory.
- ICM = Malmuth-Harville (Harville 1973 horse racing; Malmuth 1987 poker): P(player i finishes 1st) = s_i/S, then recursively condition for 2nd/3rd/... Complexity is factorial in paid places: naive implementations max out ~15 players, optimized exact ~25-30. HRC published a high-accuracy MTT approximation for fields of thousands; GTO Wizard (2024) published a purely algorithmic exact-accuracy method with ~3e-9 relative error (12+ matching digits vs ground truth) scaling to thousands of players, used to evaluate terminal-node $ payoffs directly in their solver; their AI solves HU postflop ICM spots for Freezeout/KO/PKO/Satellite/Mystery-Bounty formats up to 4,096 players in seconds.
- FGS (Future Game Simulation, HRC/ICMizer): instead of applying static ICM at the current hand's terminal nodes, spawn a new Nash solve of the next hand(s) starting from the terminal stacks with blinds advanced, applying ICM only at the recursion's leaves; simulation depth is configurable; HRC measured ~+0.3% ROI improvement over plain ICM; main benefit is capturing blind-position effects that static ICM ignores.
- HU ICM is affine in stacks: with exactly 2 players remaining and payouts p1 > p2, MH-ICM equity_i = p2 + (p1 - p2) * s_i / S, an affine function of chips — so a pure HU ICM solve is strategically identical to a chip-EV solve (good solver correctness test). ICM changes HU strategy only when the HU pot is embedded in a bigger structure (other tables still playing, PKO bounties, satellite cliffs). Caveat for later multiway work: a 2-player pot inside a multiplayer ICM tournament is itself general-sum (bystanders' equities change when two stacks clash), same CFR caveat as rake.
- Bunching effect (HRC measurements): folded hands skew remaining cards high; at 7.5bb 9-max folded-to-SB, aces appear +26.5% vs uniform (3.70% vs 2.92%), kings +7.9%, deuces -7.6%; SB shove range shrinks from 77.3% to 69.3% of hands, SB-vs-BB from 62.3% to 52.5%; ~24% of the naive pushing range becomes unprofitable, worst offenders (e.g., 75o) lose up to 0.5bb. HRC computes bunching by Monte Carlo sampling of fold-to-hero sequences; nearly all 2-player solvers ignore it. Irrelevant for pure HU (nobody folds before the players act).
- Open-source landscape and licenses: b-inary/postflop-solver (Rust, DCFR, SIMD, rayon, 16-bit compressed node storage with per-node f32 scale, isomorphism handling; TreeConfig has rake_rate in [0,1] and rake_cap fields applied at terminal nodes) — AGPL-3.0, development suspended Oct 2023 (author went commercial); wasm-postflop / desktop-postflop — AGPL-3.0; bupticybee/TexasSolver (C++, benchmark: converged in 172s vs PioSolver 242s at ~0.28% accuracy, 1.6GB vs 492MB RAM) — AGPL-3.0. All AGPL: safe to read for ideas, but copying code would force AGPL on our project. DeepMind OpenSpiel (Apache-2.0, permissive) is the safe design precedent for terminal-state utility APIs (per-player returns() at terminal states).

### 本プロジェクトへの推奨

1. Terminal-payoff architecture (the key question): make terminal evaluation a THREE-STAGE, BUILD-TIME pipeline, compiled into per-terminal-node constant payoff data before CFR starts. Stage A — game rules (variant-specific) emit a TerminalDescriptor per terminal betting node: {kind: Fold(winner) | Showdown, street_ended, pot, per-player contributions, per-player stacks-after for each chip outcome}. In HU the showdown outcome set is just {P0 wins, tie, P1 wins}, and the pot is fixed per terminal node, so this is tiny. Stage B — trait RakeModel { fn rake(&self, t: &TerminalDescriptor) -> Chips } with impls NoRake, PercentCap { rate, cap, no_flop_no_drop: bool }, GgPreflopRake, etc.; subtract from the pot before distribution, split rake on chops. Stage C — trait UtilityModel { fn utilities(&self, stacks_after: &[Chips]) -> [f64; N] } with impls ChipEv (identity), Icm { payouts } (Malmuth-Harville), Fgs { depth } (recursive solve), Pko/Bounty. Because rake and ICM depend only on chip outcomes — never on which private cards produced them — you evaluate these traits O(#terminals x #outcomes) times at tree-build time and store, per terminal node, precomputed (value_win, value_tie, value_lose) per player. The CFR hot loop (range-vs-range showdown evaluation, SIMD over hand matchups) then multiplies against constants with zero dynamic dispatch. This single decision makes rake, ICM, FGS, and bounties pluggable without touching the solver core, and it is exactly why commercial ICM solvers can reuse their cEV cores.\n\n2. Do NOT bake the zero-sum assumption into the solver core. Rake and multiplayer-embedded ICM both make the game general-sum, so never derive P1's counterfactual value as -P0's; store/compute both players' utilities independently (keep an optional zero-sum fast path for unraked cEV if profiling justifies it). Report exploitability per player via best response against the opponent's average strategy — in raked games the two numbers differ and their sum is the meaningful convergence gap. Cite/rely on Gibson et al. (arXiv:1305.0034): CFR in 2p general-sum has weaker guarantees (no iteratively strictly dominated strategies) but converges near equilibrium in practice; this is the industry-standard approach.\n\n3. Make the postflop model pluggable for the preflop solver, mirroring the commercial spectrum: trait PostflopModel with impls (a) FullTree over weighted flop subsets (start with Pio-style 25/49/95/184-flop subsets; solving all 1,755 iso-flops is the gold standard), (b) BucketedAbstraction + MCCFR (Monker-style; imperfect-recall buckets, 64-16k per street, features = equity distribution + equity realization a la Johanson et al. 2013), (c) EquityShowdownModel (HRC-v1-style: exact all-in equity at preflop all-in terminals, multiplier-based equity realization for non-allin pots) for fast/cheap preflop iteration. This gives you an HRC-fast mode and a Pio-accurate mode on one tree API. Preflop all-in terminals need exact range-vs-range equity enumeration with card removal (blockers) regardless of model.\n\n4. Algorithm defaults: DCFR with alpha=1.5, beta=0, gamma=2 (canonical Brown & Sandholm values); consider gamma=3 + power-of-4 average-strategy resets (b-inary's empirically better variant); alternating updates. Store regrets/average strategy as i16 with per-node f32 scale (b-inary precedent) to roughly halve memory — for HU preflop full-tree with a few bet sizes, budget for the 64-128GB class, or use flop subsets to fit smaller.\n\n5. ICM: implement exact Malmuth-Harville for <=10-15 players first (recursive with memoization over remaining-player subsets); keep the UtilityModel interface ready for a large-field approximation later (HRC's high-accuracy MTT method; GTO Wizard's exact method is proprietary). Implement FGS as a UtilityModel that recursively invokes the solver on the next hand with blinds advanced and ICM at the leaves (depth parameter; cache aggressively). Two cheap correctness tests fall out of the affine-HU fact: (i) a pure HU ICM solve must produce the same strategy as the cEV solve; (ii) ICM utilities must sum to total prize pool at every terminal.\n\n6. Bunching/card removal: skip for HU (provably no effect — no prior folders), but design chance/range handling as weighted per-player hand distributions, including retained distributions for folded seats, so multiway bunching later is just a reweighting of chance nodes (HRC-style Monte Carlo over fold-through sequences), not an architecture change.\n\n7. Licensing: treat b-inary/postflop-solver and TexasSolver as read-only references (both AGPL-3.0 — code reuse would infect the project); OpenSpiel (Apache-2.0) is safe to borrow API/design patterns or code from. If we ever want to publish permissively (MIT/Apache-2.0), all rake/ICM/DCFR logic must be written from scratch — the concepts above are all published in papers/blogs, so that is not restrictive.

## CFR ソルバーの性能エンジニアリング


### 概要

Performance engineering for CFR poker solvers is dominated by one architectural decision made up front — vector-form (public-tree) CFR — plus a small set of cheap algorithmic wins (DCFR/CFR+ discounting and flooring, suit isomorphism), after which parallelism and memory quantization are largely engineering exercises. In vector-form CFR (Johanson et al. 2011, used by DeepStack, Libratus, PioSOLVER, and b-inary/postflop-solver), the solver walks the public tree once while carrying per-hand reach-probability vectors ("ranges", up to 1326 combos) and returning per-hand counterfactual-value vectors; regret and strategy updates become contiguous f32 array operations that auto-vectorize well and map directly onto structure-of-arrays storage. The strongest open-source reference is b-inary/postflop-solver (Rust, AGPL-3.0, development suspended Oct 2023): DCFR with gamma=3.0, rayon multithreading, assembly-verified auto-vectorization, optional 16-bit-integer storage with a single f32 scale per node, and suit isomorphism. Its desktop build solves the PioSOLVER "3betpotFAST" flop preset to 0.1%-pot exploitability in 27 s on a Ryzen 7 3700X (16 threads, 679 MB), beating PioSOLVER (60.1 s, 1.41 GB) and GTO+ (41.7 s, 705 MB) on the same machine — proof that a small, careful Rust codebase matches commercial solvers.

Memory budgets are well documented: PioSOLVER flop trees run 500 MB–4 GB for single bet sizes, ~5.9 GB for 25bb HU dual sizes, ~7.8 GB for 100bb 6-max dual sizes; 16 GB RAM covers almost all postflop work, and typical flops solve in 1–5 minutes (rivers in seconds). 16-bit quantization (i16 regrets/strategies + per-node scale) halves memory (1.25 GB → 660 MB in the wasm-postflop benchmark) with no measurable strategy divergence at 0.1%-pot accuracy. Pluribus stored regrets as 4-byte ints and skipped extremely-negative-regret actions on 95% of MCCFR iterations, computing its blueprint in 12,400 core-hours under 512 GB; Cepheus used a disk-backed 10.9 TB trunk/subgame decomposition — the precedent for streaming preflop solves. On algorithms, DCFR (alpha=1.5, beta=0, gamma=2) and CFR+ flooring are essentially free order-of-magnitude iteration reductions; regret-based pruning and dynamic thresholding add up to about two further orders of magnitude on large trees; warm-starting from a coarser abstraction costs one tree traversal (Brown & Sandholm, AAAI-16).

GPU CFR is real but low priority for a research CPU solver. Kim (arXiv 2408.14778) reformulates CFR as dense/sparse matrix-vector products, reporting up to ~401x vs OpenSpiel Python and ~204x vs OpenSpiel C++ — but OpenSpiel's scalar CPU baselines are slow, so multipliers vs a hand-optimized vector-CFR CPU solver would be far smaller; the follow-up (arXiv 2605.14277) claims up to ~18,889x/~3,413x for sequence-form CFR variants (CFR+, DCFR, PCFR+) at high memory cost. Open implementations exist (uoftcprg/gpugt "NoRegret", MIT, Python+CUDA, small games only; cfrx in JAX, MIT, Kuhn/Leduc only); the only GPU product solving real NLHE trees, TexasSolver GPU, is "free for personal use" but not clearly open source. Rust-side SIMD guidance: std::simd remains nightly-only indefinitely; stable options are the wide crate, pulp (built-in runtime multiversioning, powers faer), or core::arch intrinsics (mostly safe since Rust 1.87) — but a research solver compiled with -C target-cpu=native can lean on auto-vectorization first and add explicit kernels only where cargo-show-asm shows failures (float reductions need manual multi-accumulator chunking since LLVM won't reassociate floats).


### 主要な所見

- Vector-form (public-tree) CFR is the foundational optimization: carry per-hand range vectors (<=1326 combos) down the public tree and return per-hand counterfactual-value vectors, so regret-matching/updates become contiguous array ops. Introduced by Johanson et al. 2011 for accelerated best-response; used by DeepStack, Libratus, PioSOLVER, and b-inary/postflop-solver.
- b-inary/postflop-solver (Rust, AGPL-3.0-or-later, suspended Oct 2023): DCFR with gamma=3.0 (vs paper's 2.0), alpha=1.5/beta=0, cumulative-strategy reset at power-of-4 iterations, rayon multithreading, auto-vectorization verified by reading assembly output ('unsafe Rust in hot spots'), optional 16-bit integer storage with one 32-bit scale factor per node, turn/river suit isomorphism, monotone-flop shortcuts.
- Benchmark (wasm-postflop README, Ryzen 7 3700X, PioSOLVER '3betpotFAST' flop preset, target exploitability 0.1% of pot): Desktop Postflop 16-bit 27.0 s @16 threads (679 MB); GTO+ 41.7 s (705 MB); PioSOLVER 60.1 s @6 threads (1.41 GB); WASM 32-bit float 45.5 s (1.25 GB). All three solvers returned nearly identical strategies (equity 55.30-55.35%, same bet frequencies). WASM runs ~2x slower than native.
- 16-bit quantization: i16 regrets/strategies plus a single f32 scale per node halves memory (1.25 GB -> 660 MB on the 3-bet-pot benchmark) with no accuracy loss at 0.1%-pot targets; per-iteration cost was ~29% higher in the WASM build but the native 16-bit build was still the fastest solver tested. Pluribus similarly stored regrets as 4-byte ints instead of 8-byte doubles.
- PioSOLVER memory/timing reference points: single-bet-size flop trees 500 MB-4 GB; wide HU ranges ~1.9 GB; 25bb HU dual bet sizes 5.9 GB; 100bb 6-max dual sizes 7.8 GB; 16 GB RAM 'rarely limits' postflop trees. Typical flop spots solve in 1-5 min, turn spots 8-14 min, rivers in seconds; scaling is 'linear with number of physical cores'; its standard benchmark (few iterations on a 2.2 GB tree) went from ~10 s (i7-3770, 2015) to ~0.7 s on current top CPUs.
- DCFR parameters alpha=1.5, beta=0, gamma=2 (Brown & Sandholm 2019, arXiv 1809.04040) empirically dominate vanilla CFR and often CFR+; CFR+'s regret flooring (reset negative regrets to 0) plus linear averaging is a free large win and inherently skips accumulating negative-regret baggage. 'Faster Game Solving via Hyperparameter Schedules' (arXiv 2404.09097) shows further gains from scheduling the discount exponents.
- Pruning: Regret-Based Pruning (Brown & Sandholm NIPS-15) temporarily skips negative-regret actions; Total RBP (arXiv 1609.03234) also reduces space and provably prunes actions not in any equilibrium best response; Dynamic Thresholding (AAAI-17) prunes low-probability actions on the fly. Literature reports up to two orders of magnitude speedup on large games. Pluribus skipped extremely-negative-regret actions in 95% of MCCFR iterations; blueprint computed in 8 days / 12,400 core-hours on a 64-core server, <512 GB RAM.
- Warm starting (Brown & Sandholm AAAI-16): any strategy pair can warm-start CFR at the cost of a single tree traversal without hurting convergence bounds; the canonical use is solving a coarser abstraction (fewer bet sizes, flop subset) first — directly applicable to preflop solving with postflop warm starts.
- GPU CFR: Kim, 'GPU-Accelerated CFR' (arXiv 2408.14778) casts CFR as dense/sparse matrix-vector ops, up to ~401x vs OpenSpiel Python and ~204x vs OpenSpiel C++ (CPU), explicitly trading much higher memory for parallelism; open implementation uoftcprg/gpugt ('NoRegret', MIT, Python+CUDA, CFR/CFR+/DCFR/PCFR+, small games only). Follow-up 'Parallelizing CFR' (arXiv 2605.14277) claims up to ~18,889x vs OpenSpiel Python / ~3,413x vs C++ for sequence-form CFR. Caveat: OpenSpiel baselines are scalar and slow; gains over a hand-vectorized CPU solver would be far smaller. 'Real-Time Parallel CFR' (arXiv 2605.19928) gets only 3.3-3.4x over single-thread on HUNL postflop (7-stage pipeline, infoset+tree-node parallelism, GPU NN leaf evaluation, ~47-54 ms/iteration on >1e9-history trees, NVIDIA DGX Spark).
- No mature open-source GPU NLHE solver exists: TexasSolver GPU is 'completely free for personal use' but its GPU code is not clearly open source; cfrx (JAX, MIT) only handles Kuhn/Leduc. The mature OSS solvers (postflop-solver, TexasSolver CPU) are all CPU-only.
- TexasSolver (C++, AGPL-3.0 with commercial licensing offered): solved an SPR=10 flop tree in 172 s vs PioSOLVER's 242 s at 6 threads with matching results (0.275% vs 0.29% accuracy), but used 1.6 GB vs Pio's 492 MB — speed bought with a less compact tree representation.
- GTO Wizard AI (proprietary, neural/depth-limited): 100bb HU single-raised-pot flop solved to 0.22%-pot accuracy in 6 s on 2 cores/8 GB vs PioSolver's 4862 s to 0.23% on 16 cores/128 GB; average flop exploitability 0.12% pot across 900 spots; beat Slumbot for 19.4 bb/100 over 150k hands — the NN-value-function route is a separate research track, not an incremental optimization.
- Parallelization pattern used in practice: partition work over independent chance branches (49 turn cards x 48 river cards) and post-action subtrees so each thread owns disjoint regret/strategy memory — no locks or atomics needed (Rust: split_at_mut / per-subtree ownership + rayon). Cepheus split HULHE into a trunk plus subgames assigned to separate compute nodes; PioSOLVER confirms near-linear scaling with physical (not logical) cores, indicating memory-bandwidth-bound workloads — which also caps NUMA benefit unless subtree memory is node-local.
- Rust SIMD landscape (2025-2026): std::simd is nightly-only indefinitely; stable choices are the 'wide' crate (stable, x86/NEON/WASM), 'pulp' (runtime multiversioning, proven by faer), or core::arch intrinsics (mostly safe to call since Rust 1.87). Elementwise f32 loops auto-vectorize under -C target-cpu=native, but float reductions do not (LLVM won't reassociate floats) — use multiple accumulators/chunked sums. Verify with cargo-show-asm. Runtime multiversioning only matters for distributed binaries, not a research tool built with target-cpu=native.
- Suit isomorphism: 22,100 flops reduce to 1,755 strategically distinct flops (~12.6x); within a postflop tree, isomorphic turn/river branches are merged (postflop-solver does this). Preflop solving iterates over the 1,755 canonical flops (or smaller weighted subsets of 49-184 flops) — an embarrassingly parallel axis. Disk-backed precedent: Cepheus's HULHE solution used 10.9 TB compressed disk storage; MonkerSolver preflop solves want 64 GB+ RAM with abstraction bucketing.
- Storage arithmetic: per infoset you need cumulative regret + cumulative strategy arrays of size (actions x hands); at f32 that is 8 bytes per action-hand pair, at i16, 4 bytes. This matches observed sizes: a 100bb 3-bet-pot flop tree with several sizes ~ 0.7-1.4 GB f32, ~660-680 MB i16.

### 本プロジェクトへの推奨

Adoption order for our Rust HU-NLHE solver, ranked by win-per-complexity:

1. Bake vector-form CFR into the core from day one (not an optimization — an architecture). Public-tree traversal carrying per-hand f32 range vectors; regrets/strategies in arena-allocated, structure-of-arrays contiguous slices per node (regret[action][hand] action-major). This is what makes everything downstream (SIMD, quantization, partitioned parallelism) cheap. Make node storage an associated type / trait (f32 backend now, i16-quantized backend later) — this also cleanly supports the planned rake/ICM axes since payoff evaluation stays at terminal-node closures over hand vectors.

2. DCFR + CFR+ flooring immediately: alpha=1.5, beta=0, gamma=2 (consider gamma=3 like postflop-solver), floor negative cumulative regrets, reset/discount the average strategy early (postflop-solver resets at power-of-4 iterations). Days of work, roughly an order of magnitude fewer iterations than vanilla CFR. Expose the (alpha, beta, gamma) triple as config to support hyperparameter-schedule experiments later.

3. Suit isomorphism: canonical turn/river branch merging inside postflop trees (~3-4x tree shrink on non-monotone boards), and the 22,100-to-1,755 canonical flop reduction for the preflop layer.

4. Rayon parallelism with lock-free partitioned updates: parallelize over chance branches (turn/river deals) and independent post-action subtrees where each task owns disjoint regret memory (split_at_mut, no atomics). Expect near-linear scaling with physical cores; don't chase hyperthreads or NUMA tuning initially — the workload is memory-bandwidth-bound.

5. SIMD, in this order: (a) write auto-vectorization-friendly loops (flat f32 slices, no branches in inner loops, multi-accumulator sums for reductions), build with -C target-cpu=native, verify hot loops with cargo-show-asm; (b) only where codegen fails, add explicit kernels — 'wide' crate for stable Rust simplicity or 'pulp' if we ever ship multiversioned binaries; avoid nightly std::simd as a hard dependency (feature-gate it at most). This is exactly the postflop-solver recipe that beat PioSOLVER.

6. 16-bit quantized storage backend (i16 + one f32 scale per node) once f32 results are validated: halves memory, doubles SIMD lanes, proven to preserve accuracy at 0.1%-pot targets. Gate behind the storage trait from step 1 so A/B validation is trivial.

7. Pruning: CFR+ flooring already gives implicit skipping; add regret-based pruning / dynamic thresholding when we attack preflop-scale trees (that's where the up-to-100x pruning wins live). If we add MCCFR for blueprint-style solving, adopt Pluribus's 95%-of-iterations negative-regret skip.

8. Warm starting for the preflop layer: solve a coarse tree (fewer bet sizes, 49-flop subset) and warm-start the full solve via Brown & Sandholm's single-traversal method; also design checkpoint/resume (serialize quantized state with bincode+zstd like postflop-solver) so long preflop runs are restartable.

9. GPU: defer. Published GPU-CFR speedups are measured against slow OpenSpiel baselines, no OSS GPU NLHE solver exists to crib from, and the sequence-form matrix formulation is memory-hungry. Revisit only for (a) batch-solving all 1,755 flops for preflop (embarrassingly parallel — multi-machine CPU may be simpler), or (b) a deliberate research track on depth-limited solving with NN value functions (the GTO Wizard AI route, 6 s flop solves), which is a different project, not an optimization.

Performance target to validate against: a 100bb 3-bet-pot flop tree with 3-4 bet sizes solved to 0.1%-pot exploitability in ~30-60 s on an 8-16-core desktop within ~0.7-1.4 GB (f32) or ~700 MB (i16). Desktop Postflop's 27 s / 679 MB on a Ryzen 7 3700X is the bar.

License discipline: postflop-solver and TexasSolver are AGPL-3.0 — read for design ideas, never copy code unless we accept AGPL for the whole project; cfr-edge and opensolver are unlicensed (all rights reserved) — ideas only; gpugt/NoRegret and cfrx (MIT) and OpenSpiel (Apache-2.0) are safe to borrow from.

## ビューワー・ツーリング・I/O フォーマット


### 概要

The dominant open-source precedent for a Rust solver + viewer stack is the b-inary trio: the postflop-solver crate (solver core), wasm-postflop (browser UI), and desktop-postflop (Tauri port of the same UI). All three are AGPL-3.0 and development was suspended in Oct 2023 when the author went commercial, but they remain the reference architecture: a pure-Rust core exposing PostFlopGame/TreeConfig/CardConfig/ActionTree with solve()/solve_step(), exploitability and EV queries, node navigation (play/apply_history), and bincode(+zstd) save/load; a Vue 3 + Pinia + Chart.js frontend; wasm-pack/wasm-bindgen bindings running in Web Workers via Comlink with SharedArrayBuffer multithreading (requires COOP/COEP cross-origin isolation); and, for desktop, the identical Vue UI over Tauri IPC instead of WASM bindings. Benchmarks (16 threads, 0.1% pot exploitability target): Desktop native 27s/679MB, WASM 32-bit 45.5s/1.25GB, WASM 16-bit 57.2s/660MB, GTO+ 41.7s/705MB, TexasSolver 182.6s/2.84GB — the 16-bit-int-with-f32-scale compression halves memory for ~25% time cost.

The commercial ecosystem defines the de-facto interface standards. PioSOLVER's UPI ("Universal Poker Interface", modeled on chess's UCI) is a line-based stdin/stdout text protocol: node IDs like r:0:b100:c:8h:c:b50:As (cumulative bet amounts, c=check/call, b=bet/raise), commands like load_tree/dump_tree/build_tree/go/stop/set_accuracy/show_node/show_strategy/show_range/calc_ev/calc_eq/lock_node/set_rake/set_icm/set_isomorphism. PioVIEWER is just a UPI client of the engine process, and third parties built an ecosystem on the protocol (jesolver reimplements UPI; pokersolverquery.py (MIT) and Pious script it from Python; GTOHelper pipes PokerTracker4 hand histories into it). Persistence uses .cfr files with three tiers: full save (huge), small save (no_rivers), very small save (no_turns) — small saves keep tree structure + early-street strategies and recompute later streets on the fly during navigation; resume = load full save, continue with `go`. Aggregated reports are plain CSVs of frequencies/EV/equity per flop over (weighted) flop subsets, consumed in spreadsheets — GTO Wizard's flagship "aggregate reports" feature is the same idea behind a precomputed-solution web viewer. TexasSolver (AGPL-3.0, Qt5 GUI) shows the config-file approach: a text script of set_ commands (set_pot, set_effective_stack, set_board, set_range_ip/oop, set_bet_sizes, build_tree, start_solve, dump_result) driving a console binary that emits one output_result.json strategy tree — but full-tree JSON dumps are impractically slow/large (users report 20-minute saves), arguing for binary formats with lazy re-solve instead.

For a research solver, the minimal-effort path is: stabilize the Rust library API plus one versioned, serde-defined query/response schema first (node path in → legal actions, per-combo strategy/EV/equity arrays out), then expose that same schema through thin adapters — CLI text protocol (ideally a UPI-compatible subset to inherit existing tooling), wasm-bindgen for a browser viewer, Tauri for desktop, PyO3/maturin for notebooks (well-trodden: pyrust-poker etc.), optional axum HTTP later. OpenSpiel's experience (issue #149: no way to persist C++ CFR solver state; later research serializes full regret+policy+config state to resumable checkpoints) confirms checkpointing must be a first-class core feature: separate the resumable checkpoint (full regrets + accumulated strategy + RNG/iteration metadata + config hash) from the compact viewer artifact (average strategy only, 16-bit compressed, optionally rivers dropped).

### 本プロジェクトへの推奨

1) Stabilize the interface in this order: (a) Rust library API (solver-core crate), (b) a versioned serde data schema for queries and artifacts, (c) a CLI text protocol, and only later (d) WASM/HTTP/Python adapters. Concretely, define one `NodeQuery -> NodeReport` schema (node path in Pio-style colon notation -> legal actions, per-combo strategy weights, EV, EQ, plus range distributions for both players) and one `SolveConfig` schema; every frontend (CLI, WASM, Tauri, PyO3, axum) is then a thin adapter over the same serde types, so viewers evolve independently of the core. Version the schema explicitly (schema_version field) from day one.

2) Split the workspace as: `solver-core` (game trees, CFR variants, no I/O), `solver-formats` (serde config + artifact + checkpoint types), `solver-cli` (batch solves from TOML configs + a UPI-like interactive mode), and later `solver-wasm` (wasm-bindgen) and `solver-py` (PyO3/maturin). For research, ship the PyO3 bindings early — notebooks + pandas/matplotlib give you 80% of a 'viewer' (range heatmaps, aggregate frequency plots) for near-zero UI effort, and maturin makes this a one-day task.

3) Config files: use TOML via serde, mirroring the union of TexasSolver's set_ commands and Pio's tree-building params: board, ranges (1326-combo weight vectors or range-string syntax), pot/effective stack, per-street bet-size sets (percent/geometric/allin, raise caps), donk options, rake model (percent + cap), ICM payout vector, algorithm block (dcfr alpha/beta/gamma — default alpha=1.5, beta=0, gamma=2, but note postflop-solver found gamma=3.0 better), target exploitability (% of pot), max iterations, thread count, seed. A config file must fully reproduce a solve (hash it into the artifact for provenance).

4) Persistence: do NOT export full trees as JSON (TexasSolver's 20-minute dumps). Use bincode or postcard + zstd with a small header (magic, schema version, config hash). Implement Pio's small-save trick: store flop(+turn) average strategies and re-solve rivers on demand during navigation — this is what makes browsing large solves practical. Separately implement resumable checkpoints (full regret + cumulative strategy state + iteration count) with periodic autosave; keep checkpoint and viewer-artifact formats distinct. Use 16-bit integer storage with per-node f32 scale for the viewer artifact (proven ~2x memory saving at negligible quality cost).

5) Viewer, minimal-effort path: Phase 1 — TUI/CLI (`show_strategy`-style tables, 13x13 range grid rendered with ratatui or plain ANSI) plus CSV aggregate reports over flop subsets (this is exactly what Pio/GTO Wizard users consume; trivially implemented as a batch runner over the TOML config with per-flop rows: action frequencies, EV, EQ). Phase 2 — compile the core with wasm-bindgen and build a small web UI (a 13x13 grid + action-frequency bars per node is ~90% of what wasm-postflop shows); serve it as a static site; enable wasm-bindgen-rayon + COOP/COEP headers only if in-browser solving (not just viewing) is desired — a viewer that only loads precomputed artifacts avoids the threading/isolation headache entirely and is the recommended first web target. Phase 3 (optional) — wrap the same web UI in Tauri for a desktop app with native solving.

6) Adopt a UPI-compatible command subset (load_tree, show_node, show_strategy, show_range, calc_ev, calc_eq, go, stop, dump_tree, lock_node, set_rake, set_icm) in the CLI's interactive mode. It costs little, is the industry's de-facto standard, and existing MIT tooling (pokersolverquery.py-style wrappers, aggregation scripts) will work against your engine, giving hand-history-analysis hooks (GTOHelper-style PT4/HH pipelines) for free.

7) Licensing: decide now. If you dual-license or go MIT/Apache-2.0, treat postflop-solver/wasm-postflop/desktop-postflop/TexasSolver as read-only inspiration — no code or UI-component reuse (all AGPL-3.0). If you accept AGPL-3.0 yourself, forking wasm-postflop's Vue UI (range editor, strategy pie/bar overlays, results grid) is by far the fastest route to a polished viewer, and its adapter layer already abstracts WASM-vs-Tauri transports.

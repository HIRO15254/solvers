# GW クロスチェック記録: Ks7h2d3c8d リバー単独(BB vs BTN SRP)

- 日付 / 実行者(モデル): 2026-07-09 / メインループ = Fable 5、GW 読み取り = Sonnet サブエージェント ×2
- GW スポット: Cash 6max NL500(rake 5% cap 0.6bb)100bb General GTO。
  BTN open 2.5bb / BB call → フロップ Ks7h2d x-x → ターン 3c x-x → リバー 8d、BB first action。
  ポット 5.5bb、実効スタック 97.5bb。リバー単独サブツリーとして解いた(入場レンジ = GW の当該ノード到達レンジ)。
- config: `docs/validation/gw-check-2026-07-09-Ks7h2d3c8d-river.toml`
  (レンジは GW の Copy ボタン出力をそのまま転記。重み合計 OOP=197.3 / IP=53.1 が GW 表示 Combos と厳密一致)
- solve: iterations=3400, 最終 nash_conv=0.0588 chips(target=0.06 ≒ 0.011% pot に到達 Y), wall=25.7s
  (参考: target 0.55 ≒ 0.1% pot なら 800 iter / 6.0s で到達し、root 頻度はその後ほぼ動かない)
- 比較ノード: リバー root(BB first action)+ 深いノード x(BTN の対応)

## 既知のツリー不一致(比較前に判明していた制約)

GW はベットサイズ(36/73/155% pot)とレイズサイズ(53/84/126% of pot-after-call)を別集合で持つが、
本ソルバーの config は 1 ストリート 1 プレイヤーにつき bet/raise 共用の fraction リスト 1 本のみ
(`crates/cli/src/config.rs` の `StreetBets`)。本検証はベットサイズ集合をレイズにも流用したため、
レイズ以降のブランチは GW と厳密一致しない。root 頻度への影響は限定的(レイズ到達 ~12%)だが、
サイズ選好が絡む比較には効く(下表の IP ノード)。

## 総合判定: BORDERLINE

- 所見: エクイティ・EV は全項目 pass — レンジ処理・エクイティ計算・レーキ(percent-cap)・EV 計算という
  エンジンのコア数値系は GW と整合。頻度の borderline / fail は §8-1(ベットツリー不一致)が主因で、
  かつ config の構造的制約(bet/raise 共用サイズ)により今回は解消不能だった。
  実装バグを示唆する乖離は見つからなかった。
- フォローアップ候補: config に per-street の raise サイズ分離(`raise = [...]`)を追加すれば
  GW General ツリーを厳密再現でき、頻度比較を pass 水準で行えるはず(roadmap 検討事項)。

## 追試(2026-07-09、raise サイズ分離実装後)

`oop_raise` / `ip_raise`(bet/raise 分離、同日実装)で GW の実レイズサイズ
`[0.52631579, 0.84210526, 1.26315789, allin]` を転記して再solve(nash_conv 0.058 chips 到達)。

| 指標 | GW | 分離前 | 分離後 | 判定 |
|---|---|---|---|---|
| root check | 57.2% | 54.3% | 54.1% | borderline(不変) |
| root bet 36/73/155% | 37.2/0.9/4.7% | 38.0/0.0/7.7% | 38.3/0.0/7.6% | 不変 |
| IP ノード x: bet 73% | 27.2% | 23.9% | **27.2%** | **一致** |
| IP ノード x: check / bet36 / bet155 | 58.1/1.9/12.7% | 53.8/18.9/3.5% | 53.0/18.2/1.5% | fail(残存) |
| EV OOP / IP | 2.37/2.76bb | 2.35/2.72 | 2.35/2.72 | pass(不変) |

**結論: raise サイズ分離は必要条件だが十分条件ではなかった**。残る乖離の要因は
(1) GW はレイズメニューも対面ベットサイズごとに可変で、bet4 / bet8.5 対面のメニューは
1 本のリストでは表現不能(「段階 2」= ノード文脈依存サイズの領域)、
(2) 36% と 155% のサイズ間 near-indifference(EV が不変のままサイズ内訳だけ動く =
均衡集合内の自由度)。EV・エクイティが引き続き pass であることから、実装バグではなく
ツリー表現力+均衡多重性の問題と結論する。

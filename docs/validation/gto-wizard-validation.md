# 手順書: GTO Wizardとの出力精度クロスチェック(postflop / Mode A)

## 0. この文書の目的と使い方

GTO Wizard(以下 **GW**)の**プリセットソリューション閲覧機能**から 1 スポットの解を読み取り、
同一ゲームを本ソルバー(`solvers`)で解いて、**アクション頻度・エクイティ・EV** を突き合わせる。
GW を「独立した外部オラクル」として使い、Mode A(exact postflop)の実装バグや収束不足を検出する。

- **想定実行者**: 下位モデル(Sonnet / Haiku)でも再現できるよう、各ステップは機械的手順として書いてある。
  判断が必要な箇所は「⚠️ 判断ポイント」として明示し、迷ったら**メインループ(上位モデル)にエスカレーション**する。
- **GW 側の操作**も本手順書がカバーする(§3.0 の指示文)。実行形態は 2 通り:
  - **モード A(推奨)**: Chrome 連携を有効にした対話セッションの Claude Code
    (Claude in Chrome 拡張を接続した状態。`claude --chrome` で起動するか `/chrome` で接続)。
    ブラウザ操作ツールが使えるので、**実行者自身が §3.0 の指示文に従って GW を操作し、
    諸元書き出しから solve・突き合わせまで一気通貫**で行う。
    - メインループが上位モデルの場合、**ブラウザ読み取り(§3.0 相当)は Sonnet の
      general-purpose サブエージェントに委譲**し、メインは検品(§3.1)・判断ポイント・
      突き合わせだけを担うのがコスト面で有効(2026-07-09 の初回検証で実績あり)。
      サブエージェントには tabId・§3.0 の指示文・§3.3 の UI リファレンスをまとめて渡す。
      追加取得が要る場合、完了済みエージェントは再開できないことがあるので、
      前回の `ui_steps` を新規エージェントの prompt に引き継ぐ。
  - **モード B**: 実行者にブラウザツールが無い場合。**§3.0 の指示文を Claude for Chrome
    (ブラウザエージェント)に貼り付けて**諸元を書き出させ、実行者は §3.1 で検品して
    以降のステップを担う。
  - どちらのモードかは**セッション開始時にブラウザ操作ツールの有無で判定**する
    (無いのに GW 取得を口頭で約束しない。ツール検索をしても見つからなければモード B)。
- **1 回の検証 = 1 スポット**。結果は §7 のテンプレートに記録する。

### スコープと前提

| 項目 | 内容 |
|---|---|
| 対象 | **postflop のみ**(`kind = "postflop"`)。preflop(Mode B)は未実装(roadmap M6)なので対象外。 |
| GW プラン | **プリセット閲覧のみ**を前提(カスタムソルブ機能は使わない)。 |
| 比較対象 | アクション頻度 / エクイティ / EV(この 3 つ。優先度は §6 参照)。 |
| 前提物 | ① `cargo build --release -p cli` 済み(`target/release/solvers`)。② GW サブスクリプション。③ Claude for Chrome。 |

### ⚠️ 利用規約(必ず守る)

- 自分の GW サブスクリプションで**閲覧可能なスポットの数値を手作業で読み取る**用途に限る。
- 大量スクレイピング・自動巡回・再配布はしない。1 スポットずつ、人間の閲覧と同等のペースで読む。
- 取得した数値は本ソルバーの精度検証にのみ使う。

## 1. 全体フロー

```
[GW プリセット] --(Claude for Chrome が読み取り)--> スポット諸元
      |                                                  |
      |                                          (§2 対応表で変換)
      v                                                  v
  GW の頻度/EQ/EV                              solvers 用 TOML config
   (=期待値)                                          |
      |                                          solvers solve/inspect
      |                                                  |
      +----------------- §6 で突き合わせ ----------------+
                              |
                        §7 に結果記録
```

手順は 5 ステップ:

1. **§3** GW からスポット諸元を取得(Claude for Chrome)。
2. **§4** 諸元を `solvers` の TOML config に変換。
3. **§5** solve を実行(収束を確認)。
4. **§6** `inspect` で出力を読み、GW と突き合わせ。
5. **§7** 結果を記録し合否判定。

## 2. GW → solvers 対応表(最重要リファレンス)

| GW で読む項目 | solvers TOML フィールド | 変換ルール / 注意 |
|---|---|---|
| ボード(フロップ/ターン/リバー) | `game.board` | 空白区切り。例 `"Qs Jh 2h"`。カード数(3/4/5)が開始ストリートを決める。 |
| OOP のフロップ入場レンジ(重み付き) | `game.oop_range` | §4.2 のレンジ転記手順。重みは `AA:0.5` 構文。 |
| IP のフロップ入場レンジ(重み付き) | `game.ip_range` | 同上。 |
| 開始ポット | `game.pot` | 整数チップ。**単位規約は §4.1**。 |
| 実効スタック(behind) | `game.effective_stack` | 整数チップ。pot と**同じ単位**で。 |
| 各ストリートのベット/レイズサイズ(%ポット) | `game.bets.{flop,turn,river}.{oop,ip}` | **%→分数**(75% → `0.75`)。意味論は §4.3。 |
| レイズ上限(1 ストリートあたりのベット+レイズ回数) | `game.bets.{street}.max_raises` | GW のツリー深さに合わせる。既定 2。 |
| レーキ(キャッシュ) | `[rake]` | §4.4。ChipEV スポットなら省略(=NoRake)。 |
| ICM(MTT) | `[utility]` | §4.4。通常は ChipEV スポットを選ぶ(ICM は当面対象外推奨)。 |

**⚠️ スポット選定の指針(検証の成否を左右する)**:

- **最初は「ChipEV / レーキなし・単一ベットサイズ・浅めのツリー」のスポットを選ぶ**。GW でベットサイズが
  1 ストリート 1 サイズに近いスポットほど、ソルバーのツリーと**厳密に一致**させやすく、乖離の切り分けが容易。
- **GW のライブラリでの推奨フィルタ(2026-07-09 調査)**: 「⚙ Change」→ Solutions=Cash、
  Postflop bet sizes=**Single Size**(1 ノード 1 サイズ)、Rake=**cEV**(レーキなし)が選べる
  (6max / Heads-up とも)。従来の Multi Size(Simple/Simplified/General)より圧倒的に転記しやすい。
  ライブラリのフィルタボタンは**クリックした瞬間に適用される**(Apply なし)ことに注意。
- **⚠️ ただし GW はどのソリューション種別でもサイズを「ノードごとに」AI が選ぶ**(例: Single Size
  cEV の Ks7h2d で、同じターンでも x-x ラインは 33%、bet-call ラインは 185%/67%。フロップも
  donk 116% / stab 33% / XR 33% / 3bet 68% と全部違う)。solvers の config はストリート×プレイヤー
  単位の固定 fraction なので、**マルチストリートのツリー厳密一致はどのみち不可能**。厳密一致が
  成立するのは**リバー単独サブツリーだけ**(サイズが「今見えているノードの分」で完結するため)。
  マルチストリート検証は近似ツリーで行い、頻度は「均衡集合内の別点」問題(§6.4)を織り込んで判定する。
- GW が 1 ノードに複数サイズ(例 33% / 75% / 150%)を持つスポットは、その全サイズを TOML に列挙する必要があり、
  ツリーが巨大化(メモリ・時間)する。初回検証には**避ける**。
- リバー単独 / ターン単独のスポット(ボード 5 枚 / 4 枚)は木が小さく、数秒で解けて反復も速い。**練習・回帰に最適**。
- **リバー単独スポットの作り方(GW プリセットから。2026-07-09 実績レシピ)**: GW にストリート単独の
  プリセットは無いが、フロップスポットを check-check / check-check で降りればよい:
  1. SRP のフロップスポットを開き、フロップ x-x → ターンカード選択(ブランクを選ぶ)→ ターン x-x
     → リバーカード選択(ペア/フラッシュ/ストレートを完成させないカードを選ぶ)。
  2. リバーの OOP first action ノードで、**両者の到達レンジを Copy**(§3.3)。x-x 経由なので
     ポット・スタックはフロップ開始時と同じ。
  3. solvers 側は `board` に 5 枚書き、`[game.bets.river]` だけ定義した config にする(§4.6 の
     雛形から flop/turn セクションを削る)。到達レンジがそのまま入場レンジになる。
  - 到達レンジは GW の均衡戦略で重み付けされた「多数の中途半端な重み」を含むが、Copy 文字列が
    フル精度なので転記誤差は出ない(手動転記なら §3.2 の⚠️どおり避けるべきパターン)。

## 3. ステップ 1 — GW からスポット諸元を取得(Claude for Chrome)

**最初にログイン確認**: `https://app.gtowizard.com/solutions` を開き、Google/Facebook/Apple の
SSO ボタンが並ぶログイン画面が出たら**未ログイン**。SSO 認証はエージェントが代行できないので、
ユーザーにログインを依頼して待つ(ログイン済みなら Study 画面のプリフロップグリッドが出る)。

§0 の実行形態に従う。**モード A**(実行者にブラウザ操作ツールがある)なら、§3.0 の指示文を
**自分自身の作業手順として**実行し、出力フォーマットどおりに諸元を書き出してから §3.1 で
セルフチェックする。**モード B** なら §3.0 の指示文を Claude for Chrome にそのまま貼り付け、
戻ってきた出力を §3.1 のチェックリストで**全項目埋まっているか検品**する。欠けがあれば
「未取得項目: ___ を追記して」と差し戻す。

### 3.0 Claude for Chrome への指示文(コピペ用)

初回検証(推奨スポット条件込み)の指示文。2 回目以降は冒頭のスポット条件を差し替えて使う。

```
GTO Wizard (app.gtowizard.com) にログイン済みのタブで、ソリューション閲覧機能を使って
以下の条件のスポットを 1 つ開き、諸元を読み取ってください。目的は自作ソルバーの精度検証で、
必要なのは 1 スポット分の手作業閲覧だけです。大量取得・自動巡回はしないでください。

■ スポット条件(初回検証用)
- Cash / Heads-Up または Blind vs Blind など 2 人参加になるスポット
- ChipEV(レーキなし)設定があればそれを選ぶ。なければレーキ設定(rate%, cap)を必ず控える
- ベットサイズが少ない「シンプル」系ソリューション(1〜2 サイズ)があれば優先
- プリフロップは最も標準的なライン(例: SRP = オープン + コール)でフロップに入る
- フロップは適当な 1 枚レインボー系ボード(例: K72r, QJ2tt など)でよい

■ 読み取り手順
1. スポットを開いたら、まずソリューション設定(スタック深度、レーキ、ベットサイズ
   ツリー設定)を画面から読み取る。設定画面/ツールチップに出るサイズ一覧
   (フロップ/ターン/リバー × OOP/IP、レイズ回数上限が分かればそれも)を控える。
2. フロップ到達時点の「ポットサイズ(bb)」と「実効スタック(bb)」を控える。
3. 両プレイヤーの入場レンジ(フロップ到達レンジ)を読み取る。レンジ表示タブで、
   重みが 100% でないハンドはカーソルを当てて正確な重み(%)を確認する。
   テキストコピー/エクスポート機能(レンジ文字列のコピー)があればそれを最優先で使い、

5. 同ノードでのレンジ vs レンジのエクイティ(OOP 視点, %)と、表示があれば EV

6. 代表ハンドを 4 個選び(強ハンド1・中間1・ドロー/エアー2)、それぞれの
   アクション別頻度(%)と、表示があればハンド別 EV・EQ を読み取る。

■ 出力フォーマット(このままの形式で全項目を埋めて返す。読み取れなかった項目は
「N/A(理由)」と書く。空欄のまま省略しない)

spot_id: <ソリューション種別/ポジション/ライン を 1 行で>
solution_type: <Cash HU 100bb ChipEV / NL500 rake5%cap3bb など>
positions: OOP=__, IP=__
preflop_line: __
stack_bb: __

board: __ __ __
bet_tree:
  flop:  oop=[__%] ip=[__%] max_raises=__(不明なら N/A)
  turn:  oop=[__%] ip=[__%] max_raises=__
  river: oop=[__%] ip=[__%] max_raises=__
oop_range: <ハンド:重み のカンマ区切り、またはコピーしたレンジ文字列>
ip_range:  <同上>
compare_node: flop OOP first action (root)
gw_values:
  freq: <action>=__%, <action>=__% ...
  eq_oop_vs_ip: __%(定義: raw か realized か表示名を添える)
```

### 3.1 検品チェックリスト(戻ってきた出力に対して)

数値の取りこぼしが後段の乖離原因になるため、**全項目を埋めるまで次に進まない**。

```
[ ] ゲーム種別:   Cash / MTT、ChipEV か否か、レーキ設定(rate%, cap)
[ ] 実効スタック: ___ bb
[ ] ポジション:   OOP = ___(例 BB)、IP = ___(例 BTN)
[ ] プリフロップアクション: ___(例 BTN open 2.5bb, BB call) → これが入場レンジを決める
[ ] 開始ポット:   ___ bb(フロップ開始時)
[ ] ボード:       ___ ___ ___ [___ ___]
[ ] OOP 入場レンジ: 13x13 グリッド(各ハンドの重み/頻度)
[ ] IP 入場レンジ:  13x13 グリッド(各ハンドの重み/頻度)
[ ] ベットサイズツリー: フロップ OOP=[__%,...] IP=[__%,...]、ターン…、リバー…、各レイズ上限
[ ] 検証したいノード(比較地点): 例 "フロップ OOP first action" や "フロップ x, IP bet 33% に OOP 対応"
```

### 3.2 レンジ読み取りの検品ポイント

- **入場レンジ**は、そのポジションが当該ラインでフロップに到達した全ハンドの重み
  (=プリフロップ戦略の頻度)。混合頻度(例 `AQo:0.5`)が含まれているのが正常で、
  全ハンド重み 1.0 のレンジが返ってきたら「重みを読んでいない」疑いがある → 差し戻す。
- ペア/スーテッド/オフスートの区別(`AA`, `AKs`, `AKo`)が保持されているか確認。
- **⚠️ 判断ポイント**: 入場レンジが「多数の中途半端な重み」を持つスポットは転記誤差が乖離の主因になる。
  初回は**入場レンジが素直な(多くが 100% or 0%)スポット**を選び直させてよい。
- Claude for Chrome の出力フォーマットは §3.0 の指示文内で定義済み。`notes:` に読み取りへの
  不安が書かれていたら、その項目は §6 の比較で重み付けを下げる(または再取得)。
- **最強の検品**: レンジ文字列の**重み合計**を計算し(§3.3 の回収スクリプト参照)、GW の同ノードに
  表示される **Combos 数と一致するか**確認する(例: OOP=197.3)。一致すれば転記誤差はほぼ排除できる。

### 3.3 GW UI 操作リファレンス(モード A 実測、2026-07-09)

実測で確認済みの UI 挙動。サブエージェントに委譲する場合はこの節を prompt に添付する。

**ナビゲーション**
- 上部のポジションボックス(UTG/HJ/CO/BTN/SB/BB)内の**アクション文字列(Fold/Call/Raise 2.5 等)を
  直接クリック**するとラインが進む(クリック後 ~1 秒ロード)。ボックス内は 1 行目 Fold / 2 行目以降
  Raise 等と行間が狭く、**誤クリックしやすい**。誤ったら位置バー左上の円形矢印
  「Reset history」で最初からやり直す。
- プリフロップ最後のコールでフロップの**ボード選択ダイアログが自動表示**される。4 行 × 13 ランクの
  カードグリッド(行 = ♠黒 / ♥赤 / ♦青 / ♣緑)。3 枚目をクリックすると自動で閉じる。
  ターン/リバーも check-check 等でストリートが終わると同じダイアログが出る(1 枚選択で閉じる)。
- 現在ノードは URL クエリ(`board=...`、`history_spot=...`)にも反映される。ボード確認に使える。

**数値の読み取り**
- **スクリーンショットの目視より `get_page_text` が正確**。数値はテキスト抽出で取り、
  スクリーンショットは位置確認・スート確認に使う(テキスト抽出はスートアイコンを落とし
  「K 9」のようにランクしか出ない。combo のスート特定にはスクショの併用が必須)。
- 右パネル「Equity chart」タブ: アクション別集計頻度(%と combos)、OOP/IP それぞれの
  EV(bb)・Equity(raw)・EQR(realized)・Combos。**数値の前に赤いダッシュ状の装飾グリフが
  付くがマイナス符号ではない**(テキスト抽出で確認済み)。
- 13x13 Strategy グリッドのセルをクリックすると右下 Summary テーブルがそのクラスの
  combo 別表示(Strategy% / EV / EQ / weight)になる。クリック後にツールチップが残って
  次のクリックを吸うことがある → 空白領域を一度クリックしてから次のセルへ。
- 左パネルの「Hands ▾」はプルダウンではなく**クリックのたびに Hands → Draws →
  EQ buckets と巡回するトグル**。カテゴリラベル(Set / Top pair / Trash hands 等)をクリックすると
  Summary がそのカテゴリに絞られる。座標でセルを数えるよりこちらが安全。解除は「CLEAR」。
- ソリューション設定は「⚙ Change」ダイアログ: Stack / Type(General 等)/ Rake / Open / 3bet の行と、
  「Rake ⓘ」ホバーでレーキ詳細(例: NL500 = 5% cap 0.6bb)。読むだけなら × で閉じれば
  現在ノードは保持される。

**URL クエリで任意ノードへ直接ジャンプ(クリックより速く確実)**
- Study 画面の URL はライン全体をクエリで持つ。手で組み立てて `navigate` すれば、クリックの
  積み重ねなしで任意ノードに到達できる(2026-07-09 実証):
  ```
  https://app.gtowizard.com/solutions?gametype=<ID>&depth=100
    &preflop_actions=F-F-F-R2.5-F-C     ← F=fold, C=call, X=check, R<総額bb>=bet/raise
    &board=Ks7h2d3c8d                    ← 3〜5 枚。ターン/リバーカードもここで指定
    &flop_actions=X-X&turn_actions=X-X&river_actions=X
    &history_spot=10                     ← 右パネルに表示するノード(意思決定の通し番号, 0 始まり)
  ```
  `gametype` は目的のソリューションを一度 UI で開いて URL からコピーする(例 `Cash6mGeneral_6mcEVR25`)。
- ヘッダのポジションボックスには**現在ラインの各ノードの選択肢(サイズ bb と %pot)が常に並ぶ**ので、
  ライン URL を変えながらヘッダを読むだけでベットツリーを高速にマッピングできる。
- 右パネルの数値(頻度・EV・EQ)は「Equity chart」タブ選択時に出る。**URL ナビゲーション後は
  タブ選択が外れることがある**ので、NO MATCH ならタブを再クリック(`find` で "Equity chart tab")。
- 右パネル「Table」タブ+グリッドセルのクリックで、下部 Summary テーブルに combo 別の
  Strategy/EV/EQ/weight が**テキストとして**出る(`get_page_text` / JS で抽出可能)。
- JS 抽出例(`javascript_tool`。ページ全文より速くて確実):
  ```js
  (()=>{const t=document.querySelector('main').innerText;
    const m=t.match(/Equity chart[\s\S]*?(?=Hands|More about)/);
    return m?m[0].replace(/\n/g,' | '):'NO MATCH'})()
  ```

**レンジ文字列の回収(モード A の推奨手順)**
- 「Ranges」タブに両プレイヤーの**現在ノード到達レンジ**と「Copy」ボタンがある。
  Copy は OS クリップボードに combo 単位のレンジ文字列(例 `3c2c: 0.236,3d3c: 1,...`、
  重みはフル精度 6 桁)を書き込む。**ブラウザ内の `navigator.clipboard.readText()` は
  フォーカス/権限の問題で失敗する**ので、ローカルシェルで回収する:
  ```powershell
  # Copy ボタンをクリックした直後に実行(OOP → 保存 → IP → 保存 の順)
  Get-Clipboard -Raw | Set-Content -NoNewline <scratchpad>\gw_oop_range.txt
  ```
  検品 3 点: ①空でない ② OOP/IP で内容が異なる ③ `combo: weight` 形式。さらに重み合計が
  GW 表示の Combos と一致すること(§3.2)。
- この文字列は **solvers の `cards::Range` 構文としてそのまま合法**(§4.2)。加工不要。

## 4. ステップ 2 — solvers 用 TOML config の作成

`examples/3betpot_fast.toml` を雛形にする。以下の規則で各フィールドを埋める。

### 4.1 単位規約(EV 比較のために重要)

- solvers はチップを**整数**で扱う。GW の bb を整数チップに写すため、**`1bb = 100 chips` で固定**すると
  小数(2.5bb 等)も整数化でき、逆変換も割り切れる(推奨)。
  - 例: 100bb → `effective_stack = 10000`、フロップポット 5.5bb → `pot = 550`。
- **ベットサイズは %ポットの分数**なので単位に依存しない(§4.3)。
- **エクイティ・頻度は %(無単位)** なので単位に依存せず直接比較できる。
- **EV は単位換算が要る**。solvers の EV はこのチップ単位/ディール。`1bb=100chips` なら
  `EV_bb = EV_chips / 100`。ただし EV は「基準の取り方」自体が GW と食い違いうるので §6.3 の注意を必ず読む。

### 4.2 レンジの転記

- GW の重み付きレンジを `cards::Range` 構文で書く。重みは `ハンド:重み`。例:
  ```
  oop_range = "TT,99,AQs,AQo:0.5,A5s:0.75,KQs"
  ```
- 重み省略時は 1.0。`22+` `A2s+` 等の範囲構文も使えるが、**GW の重みを正確に写すには
  ハンドを明示列挙する方が安全**(範囲構文は全ハンド重み 1.0 になるため)。
- **GW の Copy ボタン出力(§3.3)は無加工でそのまま使える**: combo 単位の
  `3c2c: 0.236,3d3c: 1,...` はパーサの「explicit combo + 重みサフィックス」構文に合致する
  (2026-07-09 検証済み)。手作業の 13x13 読み取りより Copy を常に優先する。
- レンジ文字列は 7KB 程度になる。TOML はエディタに貼らず、**シェルでファイルから合成**するとよい:
  ```powershell
  $oop = (Get-Content gw_oop_range.txt -Raw).Trim()
  $ip  = (Get-Content gw_ip_range.txt -Raw).Trim()
  # ヒアストリング内に $oop / $ip を展開して Set-Content
  ```
- ボード上のカードを含む combo は solver 側で自動的に 0 重みになる(転記時に気にしなくてよい)。

### 4.3 ベットサイズの意味論(GW と一致させる肝)

solver の内部計算(`crates/holdem/src/postflop.rs`)は標準のポット比コンベンション:

```
pot_after_call = 現ポット + コール額(outstanding)
レイズ上乗せ  = fraction × pot_after_call
```

- **ベット(未対面, outstanding=0)**: `fraction × 現ポット`。→ GW の「75% pot bet」= `0.75`。**そのまま一致**。
- **レイズ(対面)**: 「コールしてから、コール後ポットの fraction を上乗せ」。これは PioSOLVER / GW の
  標準 pot レイズ表記と同じ。→ GW が「pot% 表記」でレイズサイズを出しているなら `%/100` で一致。
- **GW の表示の実際(実測)**: アクションボタンは「Bet 2 (36%)」「Raise 7 (53%)」のように
  **到達総額(bb)+ %** の併記。% の定義は上記コンベンションと同一で、検算式は
  `fraction = (到達総額 − コール額) / (現ポット + コール額 × 2)`。
  例: pot 5.5bb で Bet 2 に対する Raise 7 → (7−2)/(5.5+2+2) = 52.6% ≒ 表示 53%。
  **転記前に必ずこの検算をする**(GW 表示 % は丸めなので、fraction には検算した正確な値ではなく
  bb 額から逆算した値を使う。例: `2/5.5 = 0.36363636`)。
- **bet / raise のサイズ分離(2026-07-09 追加)**: GW はベットとレイズで異なるサイズ集合を使う
  (実測例: リバーのベット 36/73/155% に対し、レイズは 53/84/126%)。config は
  `oop_raise` / `ip_raise` でレイズ専用サイズを指定できる(省略時は `oop`/`ip` に
  フォールバック = 従来挙動):
  ```toml
  [game.bets.river]
  oop = [0.364, 0.727, 1.545, 17.727]          # ベット(未対面)
  ip  = [0.364, 0.727, 1.545, 17.727]
  oop_raise = [0.526, 0.842, 1.263, 17.727]     # レイズ(対面)← GW の実サイズを検算して転記
  ip_raise  = [0.526, 0.842, 1.263, 17.727]
  ```
- **⚠️ それでも残る制約(実測 2026-07-09)**: GW は**レイズメニューも対面ベットサイズごと・
  ノードごとに変える**ため、リスト 1 本では最頻の対面(最小ベット)しか厳密化できない。
  分離転記後の実測: 対応が取れたサイズ(bet 73%)は集計頻度が厳密一致した一方、
  root は ~3% 差のまま、サイズ間で near-indifferent な内訳(36% vs 155%)は大きく割れたまま
  だった(EV・エクイティは pass のまま不変)。期待値の目安:
  - root 集計頻度: 2〜3% 程度のずれ(borderline 圏)は正常。
  - **サイズ内訳が near-indifferent なノードは一致しない**ことがある(均衡集合内の自由度)。
    サイズ別でなく check/bet(または fold/call/raise)の**大分類合計**で比較する。
  - エクイティ・EV への影響は小さい(≤1% pot)。
  - ノード文脈依存サイズ(donk/stab/対面サイズ別レイズメニュー)の完全再現は未対応
    (「段階 2」拡張。必要になったらエスカレーション)。
- サイズは effective stack を超えると自動で all-in にクランプされる。GW の「Allin」は
  `実効スタック(bb) / ポット(bb)` の分数で表現すると、ちょうどスタック額にクランプされて一致する
  (例: 97.5bb / 5.5bb → `17.72727273`)。
- **⚠️ 使用頻度 0% のサイズでも GW の実サイズを正確に写すこと(実測による強い教訓)**:
  Ks7h2d の BB donk は GW で 116% サイズ・使用 0% だが、これを「どうせ 0% だから」と 33% で
  代用したところ、solver は **33% ドンクを 37.5% 使う別の均衡**に収束した(nash_conv 0.03% pot の
  証明付き。116% に直したらドンク 3.5% に戻り、下流ノードも GW と一致)。donk のような
  near-indifferent なアクションは**可用サイズ次第で使用率が 0% にも 40% にもなる**。
  サイズ集合の一致はレイズだけでなくベットでも死活的。

### 4.4 レーキ / utility

- **ChipEV(レーキなし)**: `[rake]` `[utility]` セクションを**丸ごと省略**(既定 = NoRake / ChipEv)。← 初回推奨。
- **キャッシュのレーキ**: GW の rate/cap を写す。
  ```toml
  [rake]
  kind = "percent-cap"
  rate = 0.05        # 5%
  cap = 250          # 単位はチップ(1bb=100chips なら 2.5bb → 250)
  no_flop_no_drop = true
  ```
- **ICM**: 当面は非推奨(GW の payout 構造との一致確認が別途必要)。使うなら:
  ```toml
  [utility]
  kind = "icm"
  payouts = [__, __]
  ```

### 4.5 収束設定

```toml
[algorithm]
schedule = "dcfr"     # 既定。GW も DCFR 系なので比較に適する

[run]
iterations = 1500
check_every = 100
target_nash_conv = <0.003 × pot>   # 「0.3% pot」目安。pot=550 なら 1.65。より厳しくするなら 0.001×pot
threads = 6
```

- `target_nash_conv` は**チップ単位**(NashConv = 両者 exploitability の和 [chips/ディール])。
  `0.3% pot` を狙うなら `0.003 × pot(chips)`。GW のプリセットは概ね 0.1〜0.5% pot 相当に収束している。
- **⚠️** 収束が甘い(NashConv が目標に届かず iterations で打ち切り)と GW と乖離する。§6.4 参照。
- **実測の目安(リバー単独, ~300 ノード)**: 0.1% pot 到達に ~800 iter / 6 秒、0.01% pot に
  ~3400 iter / 26 秒。**0.1% pot から先は root 頻度がほぼ動かない**(0.5% 未満の変化)ので、
  頻度乖離が 2% を超えて残る場合に収束をさらに締めても解消しない — ツリー/レンジ側を疑う(§8)。
- **実測の目安(フロップ開始マルチストリート, ~19 万ノード)**: 100 iter ≈ 70 秒。
  **nash_conv が 0.2〜0.3% pot でも戦略はまだ未分化なことがある**(混合が 50/50 だらけ =
  DCFR の平均戦略が育っていないサイン)。マルチストリート比較は **0.05% pot 以下**
  (`target_nash_conv = 0.0005 × pot`)まで締める。この例では 400 iter / 4.5 分で 0.03% pot に到達。

### 4.6 完成 config の例(この雛形をコピーして数値を差し替える)

```toml

[game.bets.turn]
```

## 5. ステップ 3 — solve の実行

### 5.1 メモリ preflight(大きすぎる木を早期に弾く)

solve/inspect は最初に必ずツリーサイズ見積りを 1 行出す:

```
tree: nodes=... terminals=... rank_tables=... storage=XXX MiB (f32) / YYY MiB (i16)
```

- **⚠️** `storage` が搭載 RAM に対して過大(例 >8 GB)なら、ベットサイズ数 / max_raises を減らすか、
  ターン単独・リバー単独スポットに切り替える。無理に走らせない。
- **実測(Ks7h2d フロップ開始, 単一サイズ)**: max_raises 3/2/2 → 11.4 GB(f32)、2/1/1 → 2.9 GB、
  1/1/1 → 1.7 GB(i16 なら 863 MB)。**max_raises が最も効くレバー**。
- **⚠️ Windows のコミット制限**: 物理 RAM に空きがあっても `memory allocation of N bytes failed` で
  落ちることがある(コミットチャージ逼迫。ブラウザ等の常駐が多い環境)。preflight の i16 サイズが
  「空き RAM の 1/4」程度に収まる構成まで絞ると安全。

### 5.2 実行(そのまま検証に進むなら `inspect`)

`inspect` は「解いてから対話 REPL に入る」ので、検証はこれ 1 本でよい:

```bash
NO_COLOR=1 ./target/release/solvers inspect gw-check-XXX.toml
```

- 解き終わると `done: iterations=... wall=...s value_p0=... nash_conv=...` が出て `>` プロンプトになる。
- **収束確認**: 最終 `nash_conv` が `target_nash_conv` を下回っているか(=`target nash_conv ... reached` が出たか)を確認。
  出ていなければ収束不足 → §6.4。

### 5.3 (任意)非対話で数値だけ取る場合

**方法 1(推奨): REPL コマンドを stdin パイプで流す**。`inspect` は非対話でも動く:

```powershell
$env:NO_COLOR = 1
"ev`nshow`neq`ncombos 77`ncombos K9s`nquit" | ./target/release/solvers inspect gw-check-XXX.toml
```

solve → 全コマンドの出力 → 終了、が 1 回で取れる(2026-07-09 検証はすべてこの形で実行)。
深いノードは `go <action>` を列に挟む(例 `"go check`nshow`nquit"`)。

**方法 2: solve の JSON 出力**(per-combo 戦略が機械可読で欲しいとき):

```bash
# root と特定ラインの per-combo 戦略を JSON 出力
./target/release/solvers solve gw-check-XXX.toml \
  --history "" --history "x" --history "xb75" --output out.json
```

`--history` は空文字=root、以降 `x`(check)/`f`(fold)/`c`(call)/`b<額>`(bet/raise, 額はチップ)で 1 ラインを表す。
`out.json` の各 entry は `[combo_index, "AhKs", [action確率...]]`。

## 6. ステップ 4 — 出力を読み、GW と突き合わせる

`inspect` REPL の主なコマンド(`help` で一覧):

| コマンド | 出力 | GW の何と比べるか |
|---|---|---|
| `show` | 現ノードのアクションと**集計頻度** | GW のノード集計頻度(⚠️ §6.1 の重み注意) |
| `combos <class>` | **ハンド毎**のアクション確率(例 `combos AKs`) | GW の**ハンド指定戦略**(重み非依存で最も堅い) |
| `grid <action>` | 13x13 の per-class 頻度(%) | GW のアクション別ヒートマップ |
| `eq` | OOP の class 平均エクイティ(%) | GW のエクイティ表示 |
| `ev` | `ev_oop / ev_ip / expl / nash_conv / iterations` | GW の EV(⚠️ §6.3) |
| `go <action>` / `go <card>` | 子ノードへ移動(`up`/`root` で戻る) | GW でラインを進めるのに対応 |

### 6.1 頻度の比較(最優先・その 1)

- **root(最初の意思決定ノード)の集計頻度は `show` で直接比較してよい**。ここでは
  集計に使うルートレンジ重み = 実際の到達レンジなので、GW の集計頻度と整合する。
- **⚠️ 深いノードの `show`/`grid` 集計頻度は要注意**: 本ソルバーの集計はいつも**ルートレンジ重み**で
  加重する(`crates/cli/src/postflop_setup.rs` の `action_frequencies` の設計注記)。カード除去や
  上流のフォールドで**実到達レンジが変わる深いノードでは、GW の集計頻度と重みがズレる**。
  → **深いノードでは `combos <class>` を使い、ハンド毎の確率を比較する**(これは重み非依存で常に正しい)。
- **手順**:
  1. `show` で root 頻度を GW と比較。
  2. `go` で比較したいノードまで降りる(`go` の引数は `show` に出る**アクションラベル**。
     `go check` / `go "bet 182"` / インデックス `go 1`。チャンスノードはカード名 `go 3c`。
     §5.3 の `--history` で使う `x`/`b` 略記は REPL の `go` では使えない)。
  3. そのノードで**代表ハンドを 3〜6 個**選び `combos AKs` 等でハンド毎確率を GW と比較。
- **⚠️ マルチストリートの深いノード比較は「上流が一致してから」**(実測による教訓):
  上流ノードの戦略が数 % 割れると、下流の到達レンジが両者で別物になり、下流の集計頻度は
  比較不能になる(リバーで 30% 差が出ても不思議はない)。深いノードで意味を持つ比較は
  ① 上流の集計頻度がほぼ一致している場合の集計、② **選好が強い(混合でない)ハンド**の
  per-combo 確率(例: 明確な value bet / 明確な check)。near-indifferent なハンド
  (セットのスロープレー配分など)は GW と大きく割れても均衡集合内の自由度でありバグの証拠にならない。
  nash_conv が十分小さい(≤0.05% pot)ことを必ず併記する。

### 6.2 エクイティの比較(最優先・その 2)

- `eq` は OOP レンジ vs IP レンジの class 平均エクイティを 13x13 で出す(%)。
  グリッドの読み方(`eq` / `range` / `grid` 共通): **上三角 = suited、下三角 = offsuit、対角 = ペア**。
  行・列とも A→2 の順。
- GW のレンジ vs レンジ・エクイティ(通常フロップ表示にある)と比較。**無単位なので直接一致すべき**。
- **⚠️** GW の表示は 2 種類ある: **「Equity」が raw、「EQR」が realized**(Equity chart パネルに併記)。
  `eq` は**現ボードでの raw range-vs-range equity**なので **Equity の方**と比べる。
- **クラス別の比較(手軽)**: 代表ハンドについて GW のハンド EQ と `eq` グリッドの該当セルを直接比較。
  グリッドは整数丸めなので許容は ±1%。
- **レンジ集計エクイティの比較(GW の 1 個の数値と合わせる)**: `eq` は集計値を出さないので、
  クラス別重みで加重平均する: `Σ(クラス重み × eqセル) / Σ(クラス重み)`。クラス重みは
  **GW レンジファイルの combo 重みをクラスごとに合算**して得る(`range oop` の出力は
  「% of max class weight」正規化なので比率としては使えるが、レンジファイルから計算する方が正確)。
  実測例: 加重平均 46.78% vs GW 47.14%(差 0.36%、eq セルの整数丸めを含んでこの精度)。

### 6.3 EV の比較(単位換算注意)

- `ev` 行の `ev_oop` / `ev_ip` は**このチップ単位/ディール**での期待値。`1bb=100chips` なら `/100` で bb。
- **基準の変換式(確定、2026-07-09 検証)**:
  ```
  GW_EV(bb) = (ev_chips + pot/2) / 100     (1bb=100chips のとき)
  ```
  根拠: postflop ゲームは両者が `pot/2` を拠出済み・`stacks_before = effective_stack + pot/2` として
  構築され(`crates/holdem/src/postflop.rs` の `terminal()`)、表示 EV は stacks_before 基準の純増減。
  一方 GW の EV は「ポット全体を賞金とみなした期待獲得 bb」なので、自分の拠出済み `pot/2` を足し戻すと
  一致する。実測: ev_oop=−39.9 → (−39.9+275)/100 = 2.35bb vs GW 2.37bb(差 0.4% pot)。
- **整合性チェック**: `ev_oop + ev_ip = −期待レーキ(chips)`(レーキなしなら 0)。
  GW 側も `EV_OOP + EV_IP = pot − 期待レーキ` になっているはずなので相互検算できる。
- 変換式が合わない(> 数 % pot ずれる)場合のみメインループにエスカレーション。
  相対比較(2 ハンド間の EV 差、`EV/pot`)は従来どおり頑健なフォールバック。
- **⚠️ 一般和 / レーキ時**: レーキ有りは general-sum。`ev_ip ≠ -ev_oop` が正常(両者を独立に見る)。

### 6.4 許容誤差と合否

| 指標 | 一次許容(pass) | 要調査(borderline) | fail |
|---|---|---|---|
| アクション頻度(root 集計 / ハンド毎) | 絶対 ≤ 2% | 2〜5% | > 5% |
| エクイティ(range vs range) | 絶対 ≤ 1% | 1〜2% | > 2% |
| EV(EV/pot の相対 or ハンド間差) | 傾向一致 & ≤ 1% pot | 1〜3% pot | > 3% pot |

- **near-indifferent(EV がほぼ同値の複数アクション)なハンドは頻度が割れやすい**。集計頻度が合っていれば
  個々のハンドの小さな頻度差は許容してよい(均衡集合内の別点)。
- fail や borderline の切り分けは §8。

## 8. トラブルシューティング(乖離の切り分け)

乖離が出たら**この順で疑う**(上ほど頻度が高い):

1. **ベットツリー不一致** — GW のサイズ/レイズ上限を TOML が正確に写せているか。サイズが 1 つでも違うと
   使える選択肢が変わり戦略全体がずれる。→ §4.3 を再確認。特にレイズの %/倍率/総額表記に注意。
   **サイズ代用は頻度 0% のアクションでも致命的**(§4.3 の⚠️: 33% 代用ドンクが 37.5% 使われた実例)。
   乖離ノードのプレイヤーのサイズを GW の実サイズに合わせて解き直すのが最初の一手。
   **構造的に写せないケース**: GW はベット/レイズ/文脈(donk・stab 等)でノード毎に別サイズを使うが
   config は street×player 共用 1 本(§4.3 の既知の制約)。この場合の期待値: root 集計頻度 2〜3% ずれ
   (borderline)、サイズ内訳やレイズ構造が効く深いノードは大きく割れる、エクイティ・EV はほぼ影響なし
   — このパターンに合致するなら実装バグではなくツリー制約が原因。サイズ別でなく check/bet
   大分類合計で比較し、記録にその旨を書く。
2. **入場レンジの転記ミス** — 重みの読み違い・ハンドの取りこぼし。GW グリッドと TOML を 1 対 1 で突合。→ §4.2。
3. **収束不足** — 最終 `nash_conv` が target に届いていない。`iterations` を増やす / `target_nash_conv` を確認。
   `inspect` を再実行して収束させてから再比較。→ §4.5 / §5.2。
4. **単位/基準の取り違え(EV のみ)** — §4.1 / §6.3。頻度・エクイティは無単位なので単位系では乖離しない。
   EV だけズレるなら基準の問題を最初に疑う。
5. **深いノードの集計重み差(頻度のみ)** — §6.1 の⚠️。深いノードで `show` 集計を GW と比べると重みでズレる。
   `combos` のハンド毎確率で比べ直す。
6. **エクイティ定義違い** — raw range-vs-range か realizable か(§6.2)。定義を揃える。
7. **上記を潰しても頻度が root で > 5% 乖離 → 実装バグの可能性**。config・GW スクショ・`inspect` 出力を揃えて
   **メインループ(上位モデル)にエスカレーション**。既存の正当性テスト(`cfr-ref` 差分・Kuhn/Leduc・
   3betpotFAST golden、docs/architecture.md §7)と突き合わせて原因を特定する。

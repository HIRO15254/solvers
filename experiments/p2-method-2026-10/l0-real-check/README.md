# L0の誤差の測定（入力のゲームの配札、2026-10-06）

| 項目 | 内容 |
|---|---|
| 問い | L0モデルのseatの値と利得は、入力のゲームとどれだけ違うか。L0の最適応答は入力のゲームでも得をするか |
| 関連 | SOL-28（S4-1a2）、[P2方式の再設計計画](../../../docs/plans/p2-method-redesign.jp.md)の3.2節・5節 |
| 位置づけ | S4-1a2の完了条件の証拠。L0評価器そのものの検査は[L0評価器の検査](../l0-evaluator-check/README.md) |
| 再現状態 | `verified`。commit `55e84a9`のbinaryで記載の手順を実行した |

## 方法

`mw_preflop::trunk::l0::real`（実験用、製品契約の外）は、class単位のprofileを入力のゲームの配札で評価する。
配札はgameの`DealSampler`で引く。全seatの手札は互いに重ならず、5枚のboardは配った全員の手札（foldしたseatを含む）を
除いた山から引く。sampleするのはcardだけで、行動の期待値は配札ごとに公開木全体を厳密に足す。

- seat `i`の値`u_i^real`は、配札ごとの値`v_i = Σ_z Π_j π_j(z) U_z[i]`の平均。`π_j(z)`はseat `j`の手札のclassで
  profileの行動確率を経路に沿って掛けたもの、`U_z`は終端`z`の精算（chip EV）である。
- L0評価器の最適応答`β_i`（class単位の純粋な行動）を同じ配札で使い、`b_i = Σ_z β_i(z) Π_{j≠i} π_j(z) U_z[i]`を求める。
  入力のゲームでの利得は配札ごとの差`b_i − v_i`の平均（共通乱数）。`β_i`は入力のゲームでのclass単位の
  最適応答とは限らないので、この利得は入力のゲームでのclass単位の利得の下限である。
- 値は終端に残った人数`k`ごとにも分ける。L0側の内訳は評価器の`value_by_active_count`。
- `±`は配札ごとの値の標本標準偏差を√Nで割った標準誤差。L0側のMonte Carlo（T3、4人以上のshowdown）の誤差は含まない
  （[L0評価器の検査](../l0-evaluator-check/README.md)では、seedを変えたときの`g_i`の差は5.3×10⁻⁵以下）。
- 配札`d`の乱数は`blake3("solvers.p2.trunk.l0.real.v1" || seed)`を鍵にしたChaCha8のstream `d`。4096配札ずつの
  固定の塊を順に合わせるので、結果はthread数に依らない。

## 検査

- `physical_deal_values_match_independent_recursive_settlement`: 3人（rakeなし）と4人（rakeあり・side pot）の木で、
  200の配札について配札ごとの`v_i`・`k`別の値・`b_i`を参照実装と比べる（許容差1e-12）。参照実装は公開木を再帰で辿って
  seatごとの確率を掛け、全終端をgameの`settle_terminal`（cardから役を作って精算する）で精算する。最初の20配札は
  純粋なprofileでも比べ、到達確率0の部分木を飛ばす処理と、profileが通らない経路での最適応答を確かめる。
  3人・rakeなしでは、配札ごとにseatの値の和が0になることも確かめる。
- `physical_estimates_match_direct_sample_statistics_and_seed_stream`: 平均と標準誤差（seat別、`k`別、値の和、利得の和）を、
  参照実装で配札ごとに求めた値の標本統計と比べる。
- `physical_deal_estimates_are_thread_independent_and_validate_inputs`: thread数1と4で結果がbitで一致する。
  入力の誤り（配札数1、最適応答のseat数・長さ・行動番号）を拒否する。
- `exported_pure_best_responses_attain_l0_values`: L0評価器が書き出した最適応答でseatの行を置き換えて評価し直すと、
  そのseatの値が元の`BR_i`に一致する（3人・4人）。
- 既存のL0のtestに、`k`別の値の和が`u_i`に一致することを加えた。L0評価器の出力は、新しい欄と時間を除いて
  [前回の記録](../l0-evaluator-check/results/b3/20bb_300k_s0.json)とbitで一致した。
- ignoredのrelease test `real_matches_l0_in_heads_up`: 2人10bb、乱数のprofile、2^20配札で、値と利得がL0と
  5標準誤差以内で一致する。

4人以上のshowdownは、終端ごとに精算と同じpot構成（`build_rated_pots`、rakeとside potを含む）から、勝者の組ごとの
配当（odd chipはbuttonの次のseatから）を前計算して使う。2人・3人のshowdownはL0評価器と同じ、終端ごとの順位別の精算を使う。

## B1: 2人push/fold

2人ではL0が入力のゲームそのものなので、Monte Carloの値はL0の厳密な値と標準誤差の範囲で一致するはずである。
[L0評価器の検査](../l0-evaluator-check/README.md)と同じ3つのstack（5・10・20bb）で、一様・乱数（seed 1）・
暫定方式の解の3つのprofileを2^22配札（配札のseed 0）で評価した。

- 9件・2 seatの全部で、値の差は2.36標準誤差以下、L0の最適応答の利得の差は2.25標準誤差以下、
  利得の和と`NashConv`の差は1.71標準誤差以下だった（表は[results/b1/summary.md](results/b1/summary.md)）。
- 9件は同じ配札を使うので誤差は互いに相関する。BTN/SBの値の差は、一様・乱数の6件でどれも−2.05〜−2.36標準誤差だった。
  偏りではないことを確かめるため、10bbの一様なprofileを配札のseed 0〜4で2^24配札ずつ評価し直した。
  値の差は−1.77〜+1.03標準誤差、利得の差は−2.35〜+1.22標準誤差で、5本を合わせた値の差は−0.93標準誤差だった。

### 乱数とthread数への感度

- `20bb_300k_s0`を8 threadで評価し直すと、L0と入力のゲームの値がbitで一致した。
- 配札のseedを0から1に変えると、seatの値の差は−0.51〜+0.27標準誤差、L0の最適応答の利得の差は−0.66〜+1.24標準誤差、
  利得の和の差は+1.06標準誤差（いずれも2本の標準誤差を合わせた単位）だった。標準誤差は配札による揺れの大きさと合っている。

## 解釈

- L0は、どの解でもどのseatでも値を高く見積もった。暫定方式の解で最も大きいのはBBの0.026〜0.029 bbで、
  300kの解の利得`g_i`（最大0.016）より大きい。
- L0の誤差の源は、相手同士の手札の依存を無視すること（L0はheroの手札だけを条件に、相手を互いに独立に配る）と、
  foldしたseatのcardを山に残すことの2つである。一様なprofileでは行動がcardに依らないので、foldしたseatのcardは
  無作為で後者は効かず、残った相手が1人以下のk=1・k=2では前者も効かない。実際にk=1・k=2の差は0で、誤差は全部3人以上の
  showdownから来た。一様なprofileでは相手同士の手札の依存だけが違いなので、L0はこれを無視することで、3人以上の
  showdownでheroの値を高く見積もったことになる。暫定方式の解では、3人以上のshowdownに届く確率は4.6〜5.8%
  （L0で見た値）と低く、誤差の67〜86%がk=1・k=2から来た。k=1の終端の払いはcardに依らないので、そこの差は
  到達確率の差だけ、つまり相手同士の手札の依存から来る。
- L0の最適応答は入力のゲームでも得をする。30kの解では、L0の`NashConv`の91〜94%が入力のゲームでも得られた。
  300kの解では60〜69%で、L0の`NashConv`のうち0.021・0.016 bbは得られなかった。30kから300kへ、L0の最適応答が
  入力のゲームで得る利得は1/10・1/9に減り、L0の`NashConv`の減り方（1/6.5〜1/6.9）より大きい。
- L0の`NashConv`は、利得が大きい解どうしの比較には使える。L0の`NashConv`の差が0.02 bb前後より小さい解どうしは、
  入力のゲームでの良し悪しを区別できない可能性がある。
- 入力のゲームでの`NashConv`（class単位）は測っていない。L0の最適応答の利得は、その下限にすぎない。L0の均衡に近い解では、
  L0の最適応答はprofileそのものに近づき、入力のゲームでの利得の下限は0に近づく。そのような解を入力のゲームで評価するには、
  入力のゲームでの最適応答が要る。

## 時間

- 入力のゲームでの評価（16 thread）: 暫定方式の解は30kで毎秒約3.0万・3.5万配札（2^25配札で966〜1,128秒）、
  300kで毎秒約23万・31万配札（147秒・107秒）。到達確率0の部分木を飛ばせる量で速さが変わる。一様なprofileは飛ばせる部分木が
  無く、毎秒約7,300配札（4,592秒）だった。2人push/foldは毎秒1,200万〜1,600万配札。
- 同じprocessでのL0の評価は67〜91秒。8 threadの評価し直しは全体で252秒（16 threadでは227秒）。
- B3全体は7,773秒（[run_b3.log](results/b3/run_b3.log)）。

## 手順

workspace rootでGit Bashから実行する。

```sh
cargo build -p mw-preflop --release --example l0_real --example l0_eval --example trunk_tables
bash experiments/p2-method-2026-10/l0-real-check/run_b1.sh <B1の出力directory>
bash experiments/p2-method-2026-10/l0-real-check/run_b3.sh <B3の出力directory>
python experiments/p2-method-2026-10/l0-real-check/summarize.py b1 <B1の出力directory>
python experiments/p2-method-2026-10/l0-real-check/summarize.py b3 <B3の出力directory>
```

- [run_b1.sh](run_b1.sh)は表のcache（`.cache/p2-trunk`、無ければ作る）を使い、乱数のprofileを
  [hu_pushfold_check.py](../l0-evaluator-check/hu_pushfold_check.py)で作ってから評価する。暫定方式の解の行は、
  [L0評価器の検査](../l0-evaluator-check/README.md)で作った`runs/p2-method-2026-10/l0-evaluator-check/b1_<s>bb`が
  あるときだけ実行する。
- [run_b3.sh](run_b3.sh)は`runs/p2-method-2026-10/legacy-seed-noise/`の4つの解を読む。2つ目の引数で配札数を変えられる
  （既定は2^25）。
- [summarize.py](summarize.py)（Python標準ライブラリだけ）はB1・B3の表を出力する。

# P1 storageの収束と計算量（AWS、2026-10-29）

再現状態: **部分検証**（曲線・計時の生JSONを保存。最終成果物の大きな`.sol`は保持しない）。

## 変更

PF11の`auto`を変更しない。storageの精度と性能を調査した。solver codeの変更はない。

## 方法

source `00483eaff5d77a81bcec8f944d7e112858a22af3`、Rust 1.97.0、`-C target-cpu=znver3`。機械とbinary hashは[manifest](manifest.json)。木は[既存config](../memory-estimate-20261029/configs/)から生成した[実行config](results/curves/)を使う。

`convergence.py`はlab共有機で16 thread、25 iterationごとに評価し、最大10000反復、Flopとc_gtowbは360秒、Turn・Riverは180秒で停止した。時間制限はbatch単位で判定し、構築・保存時間を含まない。i16のみ既定でpow4 resetを使い、noresetは明示false。各progressを保存した。cash rakeがあるため`NashConv / 2 / 開始pot × 100`は停止指標であり零和保証でない。

`timing.sh`はbench排他lock下、各木・thread数でstorage順を巡回し各3回、warmup 2、計時5 iteration、評価3回。下表は3回の中央値（評価は各run内の3回の中央値の中央値）。peakはprocessのVmHWMで保存時peakではない。

c_gtowbは追加で0.05%まで3 storageを試みたが、labが2回Spot回収された。1台目では延長runが中断され、2台目ではf32・mixedが完了した直後に回収されて結果を持ち出せず、i16は中断した。2台目の途中snapshotではf32の200反復までしか保存できていない（[途中記録](results/storage-floor-large/)）。したがって下表のc_gtowbは最初の360秒の結果であり、0.05%への到達やfloorは未測定である。比較用runも1台目では失われたが、2台目の小さい5木は完了後に保存した。

## 判断

現時点ではPF11維持を推奨する。小さい木でもi16は後半で悪化し、0.1%よりかなり低い目標には向かない。mixedもf32より大きな誤差が観測され、いずれも木ごとの安全なfloorを事前に求める規則はこの測定から導けない。一般化できる安全余裕を設けずtargetのみでi16を自動選択する提案はしない。明示i16はメモリが重要で目標精度を利用者が判断できる場合の選択肢。f32が収まらずmixedが収まる現行のfallbackも深いtargetでの到達を保証しない。

代案は利用者指定の精度・メモリ優先、収束中の停滞診断、street別mixed precision。ただしいずれも別途仕様決定・検証が必要。resetの影響は大きく、River・Turnのi16 noresetは0.2%すら到達しなかった。floorを小さな木の最小値だけで予測してはいけない。

## 正しさ

solver codeは変更していない。曲線と速度は同じbase sourceからbuildしたbinaryで得た実測であり、比較はreplacement labで同じsourceを再buildした別binaryを使った。比較用`.sol`自体はGitへ保存しない。停止状態・実効config・評価列・計時生JSONはresultsに保存。Spot回収と再実行の詳細はmanifest参照。必須code変更検証・bitcheckはcode変更が無いため実施していない。
